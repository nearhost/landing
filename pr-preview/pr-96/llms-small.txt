# Introduction

> What Nearhost does, who it is for, and how to get a remote project open in your browser.

Nearhost opens your dev servers at trusted `https://name.test` addresses, whether they run on this machine or on another one you reach over SSH. For a remote server it uses the SSH access you already have and installs nothing there. ## Who it is for You run dev servers on your laptop, or somewhere else: a desktop under the desk, a home server, a VPS. Over there the app listens on `localhost`, and your browser is over here. Without Nearhost that means an `ssh -L` flag per port, a certificate warning, and hot reload that fails to connect. With it, each project has a name, a certificate your browser trusts, and forwards that reconnect on their own. ## What you get * **One address per project.** `https://myapp.test` today, tomorrow and after a reboot. * **Real HTTPS.** Secure cookies, OAuth callbacks and service workers behave as they do in production. * **Hot reload and WebSockets.** They travel through the same SSH connection. * **Nothing installed on the server.** No daemon, no open ports, and nothing written to your project unless you run `nearhost export`. Nearhost only keeps a socket in `~/.nearhost` there, so a coding agent on the server can reach it. If `ssh <host>` works without a prompt, Nearhost works. * **Any stack.** Nearhost routes ports. It finds them in `.env`, and [presets](/pr-preview/pr-96/docs/concepts/presets-and-registries/) teach it Compose files, Vite and Laravel Sail. You can set routes by hand for anything else. ## Quick start Install the binary: 
```sh
curl -fsSL https://nearhost.dev/install.sh | sh
```
 Start it. The first time, it offers to trust its local certificate authority so your browser accepts its certificates: 
```sh
nearhost
```
 Then press `s` to add a server, `n` to add a project on it or on this machine, and `o` to open it. Nearhost starts each project as soon as it is added, and every enabled project each time it opens. `q` quits and stops them all. The same steps from the command line, which offers to add `mini` when it is not a server yet: 
```sh
nearhost add --server mini ~/code/myapp
nearhost up myapp
```
 `nearhost doctor` checks your setup at any time. ## Where to go next * [Install](/pr-preview/pr-96/docs/getting-started/install/) covers the installer, Homebrew, npm and Linux setup. * [Add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) and [Add a project](/pr-preview/pr-96/docs/getting-started/add-a-project/) walk through each screen. * [Presets and registries](/pr-preview/pr-96/docs/concepts/presets-and-registries/) explains how Nearhost learns a framework’s ports. * [Dev servers and hot reload](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/) explains how assets and live reload reach your browser. * [SSO callback fails on a remote dev server](/pr-preview/pr-96/docs/guides/sso-callback-on-a-remote-dev-server/) fixes sign-in that breaks on a remote dev server. [HTTPS on a local dev domain](/pr-preview/pr-96/docs/guides/https-on-a-local-dev-domain/) and [ngrok loads the page, but assets point at localhost](/pr-preview/pr-96/docs/guides/ngrok-assets-on-localhost/) cover the HTTPS name and the asset URLs. ## When to use something else Nearhost serves your own browser on your own machine. To show a page to a client or a teammate, use a public tunnel service. To reach a database or another non-HTTP port, a plain `ssh -L` forward is still the right tool.

# Install

> Install the Nearhost binary on macOS or Linux, including the extra steps Linux needs.

Nearhost is one static binary for macOS and Linux, built for amd64 and arm64. Pick whichever of these fits how you install tools. ## Shell installer 
```sh
curl -fsSL https://nearhost.dev/install.sh | sh
```
 The script detects your OS and CPU, downloads the matching release from GitHub, verifies its checksum and installs to `/usr/local/bin` when that is writable, otherwise to `~/.local/bin`. It tells you when that folder is not on your `PATH`. Three environment variables change what it does: | Variable | Effect | | ---------------------- | -------------------------------------------------------- | | `NEARHOST_VERSION` | Install this release instead of the latest, as `v0.8.0`. | | `NEARHOST_INSTALL_DIR` | Install into this folder. | | `NEARHOST_SKIP_SETCAP` | Set to `1` to skip the Linux port step below. | Check the install with: 
```sh
nearhost --version
```
 `nearhost --version` needs Nearhost 0.8.0 or later. `nearhost version` prints the same, and works on releases before 0.8.0 too. ## Homebrew 
```sh
brew install nearhost/tap/nearhost
```
 ## From source With Go: 
```sh
go install github.com/nearhost/nearhost/cmd/nearhost@latest
```
 Nearhost needs Go 1.27.3 or later, the version the release binaries are built with. Go 1.21 to 1.27.2 downloads it first, unless `GOTOOLCHAIN` forbids it (some distributions’ Go packages set it to `local`). Then install Go 1.27.3 or later yourself. ## npm 
```sh
npx @nearhost/cli
```
 or `npm install -g @nearhost/cli` to keep the `nearhost` command. npm installs the binary for your machine as a platform package, such as `@nearhost/cli-linux-x64`, with no install script, so pnpm, bun and `--ignore-scripts` work too. ## Verifying a download The shell installer checks the archive against the release’s `checksums.txt`. It does not check the attestation. Releases also carry build provenance attestations, and you can check any file you downloaded with the GitHub CLI: 
```sh
gh attestation verify <file> --repo nearhost/nearhost
```
 Each archive comes with a software bill of materials, `<archive>.sbom.json`, listing the modules it was built from. The attestation covers the archives, their SBOMs and `checksums.txt`. From Nearhost 0.8.0. The macOS binaries are signed with a Developer ID certificate and notarised by Apple, so Gatekeeper runs them however you download them. A copy downloaded in a browser may need an internet connection the first time it runs, while macOS checks the notarisation with Apple. From Nearhost 0.9.0. ## Updating 
```sh
nearhost update
```
 updates Nearhost the way you installed it, after asking. See [`nearhost update`](/pr-preview/pr-96/docs/reference/cli/#nearhost-update). ## Linux setup Linux needs three things that macOS handles with a single prompt. `nearhost doctor` checks all of them. ### Allow binding ports 80 and 443 Nearhost serves HTTPS on 443 and redirects 80. A normal user cannot bind those ports, so grant the binary that one capability: 
```sh
sudo setcap cap_net_bind_service=+ep "$(command -v nearhost)"
```
 Run it again after each upgrade, because replacing the binary clears the capability. `nearhost update` prints the command when it is needed. The shell installer prints this command for you. Run from a downloaded copy at a terminal, rather than through `curl | sh`, it asks whether to run it, and only uses `sudo` if you say yes. Installed from npm, `command -v nearhost` finds the Node launcher rather than the binary, so run the command `nearhost doctor` prints instead: it names the binary itself. ### Trust the certificate authority 
```sh
nearhost trust
```
 This adds the Nearhost Local CA to the system trust store and asks for your password through `sudo`, which must be in `/usr/bin`, `/bin`, `/usr/local/bin` or `/run/wrappers/bin` and owned by root, from Nearhost 0.8.0. It uses your distribution’s own tool: | Distribution | Command it runs | | -------------- | ------------------------- | | Debian, Ubuntu | `update-ca-certificates` | | Fedora, RHEL | `update-ca-trust extract` | | openSUSE | `update-ca-certificates` | | Arch | `trust extract-compat` | ### Trust it in your browser Firefox and Chromium-based browsers on Linux keep their own certificate databases and ignore the system store. Nearhost fills them in when `certutil` is installed: 
```sh
sudo apt install libnss3-tools   # Debian, Ubuntu
sudo dnf install nss-tools       # Fedora, RHEL
```
 Then run `nearhost trust` again. It prints whether the browser stores were updated. Restart the browser afterwards. The CA’s key is not in your config folder. See [The local CA](/pr-preview/pr-96/docs/concepts/tls-and-the-proxy/#the-local-ca) for where it is and how to look after it. ## macOS and Firefox `nearhost trust` adds the CA to the System keychain, which Safari and Chrome use. Firefox keeps its own store. To cover it, install `certutil` and run trust again: 
```sh
brew install nss
nearhost trust
```
 ## Next Run `nearhost`. The first time, it offers to trust the certificate authority for you. See [First run](/pr-preview/pr-96/docs/getting-started/first-run/).

# First run

> What Nearhost shows the first time you start it, and when it asks for your password.

Start the interface with: 
```sh
nearhost
```
 It starts the proxy and every enabled project, and creates the local certificate authority, “Nearhost Local CA”, if it does not exist yet. Its key is kept in Nearhost’s data folder, not in `~/.config`. See [The local CA](/pr-preview/pr-96/docs/concepts/tls-and-the-proxy/#the-local-ca). ## Nothing to serve yet With no projects, the screen shows the Nearhost mark and “Nothing to serve yet.”, with the two ways in: 
```text
n  add a project on this machine or a server
s  add a server you reach over SSH
```
 Below them are the folder you started in, whether the certificate authority is trusted, the proxy’s ports, and, from Nearhost 0.8.0, a link to Nearhost’s page at `https://localhost:6327`, or on the port `--web-port` gives, unless that port was taken or `--web-port 0` turned it off. See [TLS and the proxy](/pr-preview/pr-96/docs/concepts/tls-and-the-proxy/). Press `n` to serve a project from this machine, or from a server you have added. Press `s` first if the project is on a machine you reach over SSH. See [Add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) and [Add a project](/pr-preview/pr-96/docs/getting-started/add-a-project/). ## Welcome to Nearhost While your system does not trust the certificate authority, a box titled “Welcome to Nearhost” opens over the screen. It says what will ask for your password: * now: trusting the local certificate authority, so browsers accept HTTPS from Nearhost’s web server * later: adding names to `/etc/hosts` Press `enter` to trust it now, or `s` to skip. Skipping lasts until you next start Nearhost, and the box comes back while the authority is still untrusted. Once it is trusted you see “The local CA is now trusted.” and the box does not appear again. Trusting installs the authority’s root certificate into your system trust store: the System keychain on macOS, your distribution’s certificate store on Linux. It is what lets your browser open `https://<alias>` without a warning. Firefox, and Chromium-based browsers on Linux, keep their own stores. Nearhost updates those too when `certutil` is installed. See [Install](/pr-preview/pr-96/docs/getting-started/install/) for the one-line setup. If you skip, the proxy still runs and Home shows `local CA ● not trusted. Run nearhost trust`. You can trust it from a terminal at any time, and `nearhost untrust` reverses it: 
```sh
nearhost trust
```
 ## The password box Two things need root: trusting the certificate authority, and adding your projects’ names to `/etc/hosts`. For both, Nearhost asks in a box titled “Password needed”, which says why: 
```text
Nearhost needs your password to add myapp.test to /etc/hosts.
```
 Type your password and press `enter`, or `esc` to cancel. The password goes straight to `sudo` and nowhere else: it is not shown, logged or saved. * **A wrong password** shows “Sorry, try again.” After three, the step stops and nothing is changed. * **Cancelling** leaves things as they were. The certificate authority stays untrusted, or the project stays stopped until you start it again. * **sudo remembers it** for a few minutes, as it does in a terminal, so a second step soon after does not ask again. * **If sudo asks every time**, because it is set up not to remember, Nearhost hands over to the terminal for the password, then comes back. `/etc/hosts` is only changed when a project starts and its names are missing, so most starts ask for nothing. See [The hosts file](/pr-preview/pr-96/docs/concepts/the-hosts-file/). ## Touch ID on a Mac macOS can let `sudo` take your fingerprint instead of your password, but it is off until you turn it on. Copy the template that macOS ships: 
```sh
sudo cp /etc/pam.d/sudo_local.template /etc/pam.d/sudo_local
```
 Then edit `/etc/pam.d/sudo_local` as root and remove the `#` from this line: 
```text
auth       sufficient     pam_tid.so
```
 Check it in an ordinary terminal. This should show the Touch ID dialog: 
```sh
sudo -k; sudo -v
```
 With it on, Nearhost may still ask for your password the first time, then use Touch ID when it next needs root. Typing the password always works. Touch ID only works at the Mac itself, not over SSH. Inside tmux or another terminal multiplexer it may also need [pam_reattach](https://github.com/fabianishere/pam_reattach). ## Home Once a project exists, the screen has a sidebar on the left, with Home at the top and each server’s projects below, and the selected row’s details on the right. Home shows: * `proxy`: whether it is serving, and on which ports * `page`: a link to Nearhost’s page at `https://localhost:6327`, or the port `--web-port` gives, once the proxy is serving. It is left out when that port was taken. Needs Nearhost 0.8.0 or later. * `local CA`: whether it is trusted, and when it expires * `hosts`: whether `/etc/hosts` has every project’s name * `config`: the path of the config file * `running`: how many projects are running, on how many servers When something needs you, a problems section lists it, with why it happened and how to fix it. Below that is the recent log. Press `l` for the full-screen log, `/` to filter the sidebar by name, and `h` to come back to Home. `?` lists every key. See [Keyboard shortcuts](/pr-preview/pr-96/docs/reference/keyboard-shortcuts/). Next: [Add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) or, for a project on this machine, [Add a project](/pr-preview/pr-96/docs/getting-started/add-a-project/).

# Add a server

> Register a remote machine that Nearhost reaches through your existing SSH setup.

A server is a remote machine you can reach with OpenSSH. Nearhost runs your own `ssh`, so your `ssh_config` applies, including `Include`, `Match`, `ProxyJump` and `IdentityAgent`. The `local` server is this machine. It always exists, needs no configuration, and cannot be removed or renamed. ## Before you start `ssh <host>` must work without prompting for anything, and the server must allow SFTP, which most do. Nearhost reads project files over SFTP. Check the first part with: 
```sh
ssh -o BatchMode=yes -o ConnectTimeout=10 <host> true
```
 If it exits 0, Nearhost can connect. If it asks about a host key or a passphrase, answer it in a normal `ssh <host>` session first. ## From the interface Press `s`. A box titled “Add server” opens over the screen, in three steps. 1. **Host.** The hosts in `~/.ssh/config` that you have not added yet are listed under the field, and typing filters them. Choose one with `↑` and `↓`, or type a host such as `dev@build.lan`. Wildcard hosts are not listed, and neither are hosts in files that `~/.ssh/config` includes, so type those. 2. **Name.** The name shown in the sidebar. It starts as the host without the user, and you can change it. `local` is taken. 3. **Check.** Nearhost connects with your SSH setup and opens SFTP. When that works, the server is saved and selected. `esc` goes back a step, and from the first step closes the box. Nothing is saved until the check passes. Adding a project can add a server on the way: choose **New server…** on its first step. ## What Nearhost stores Only the name and the host, in `~/.config/nearhost/config.yaml`. No keys, passwords or sockets are stored. 
```yaml
servers:
  - name: mini
    ssh_host: mini
```
 For a port other than 22, give the host an entry in `~/.ssh/config` with a `Port` line and use its alias. ## If the check fails The box shows OpenSSH’s error, followed by what to do: run `ssh <host>` once in a terminal to fix access. That is where OpenSSH handles unknown host keys, `ssh-add` and similar. Fix it there, then press `r` to check again. ## Afterwards Select the server in the sidebar to see its host, its projects and its log. | Key | Action | | --- | ---------------------------------------------------------------- | | `r` | Reconnect. | | `c` | Drop the connection, or connect it again. | | `e` | Edit the host and name. A new name carries over to its projects. | | `d` | Remove the server and its projects, after you confirm. | | `n` | Add a project on this server. | From the command line, `nearhost add --server <name>` run at a terminal offers to add a server it does not know yet. Nothing is installed on the remote machine. Nearhost makes a private `~/.nearhost` folder there and keeps a socket in it, so a coding agent on the server can reach Nearhost. See [How agents reach Nearhost](/pr-preview/pr-96/docs/coding-agents/how-it-works/). The only file it ever writes to a project is a `.nearhostrc`, and only when you run [`nearhost export`](/pr-preview/pr-96/docs/reference/cli/#nearhost-export).

# Add a project

> Register a directory on this machine or a server and serve it at an alias.

A project is a directory, on this machine or on a server, that runs an HTTP service. Nearhost reads the project’s files to work out its ports, then serves it at an alias, `<name>.test` unless you choose another. The service can be anything that listens on a port. ## From the interface Press `n`. A box titled “Add project” opens over the screen. Its steps are counted at the top, and steps that have nothing to ask are skipped. `esc` goes back a step. 1. **Server.** Pick `local` for this machine, or a server you have added. The selected server, or the selected project’s, is chosen already. **New server…** adds one on the way. See [Add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/). 2. **Path.** The project’s directory. On `local` it starts as the folder you ran `nearhost` in, and on a server as `~/`. See [Typing a path](#typing-a-path). 3. **Presets.** Nearhost reads ports from `.env` by itself. While no preset registry is trusted, it asks once whether to trust the official presets, which add Compose files, Vite and Laravel Sail. Choose Yes, No, or Don’t ask again. With a registry trusted, it lists the presets that suit this project, ticked. `space` unticks one, and `enter` enables the rest. See [Presets and registries](/pr-preview/pr-96/docs/concepts/presets-and-registries/). 4. **Routes.** The ports found, with a role, what each opens on this machine and a label. Ticked ports are served. The project’s web port opens `https://<alias>`, and any other `web` port opens the names it is given. A `loopback` port opens `localhost:<port>`, and an `ignore` port opens nothing. See [Routes and roles](/pr-preview/pr-96/docs/concepts/routes-and-roles/) for what each does. The line under the table says what the selected port’s role does. `space` ticks or unticks a port, and `←` or `→` changes its role. Changing one port’s role leaves the others as they are. At least one port must be `web`, and only one `web` port can go without names of its own; `enter` says so if two do. One port is the project’s web port. To serve another port as well, make it `web` and give it names of its own with `h`. If no ports were found, give the web port yourself. The opens column and the line under the table need Nearhost 0.8.0 or later. 5. **Name.** The project’s name and its alias. The name is what Nearhost calls the project: in the sidebar, the log and `nearhost up <name>`. The alias is the address your browser opens, shown after `https://`. It follows the name until you change it, unless it comes from the project’s `.nearhostrc`. `tab` moves between them. Names and aliases must be unique. The alias is the project’s [main name](/pr-preview/pr-96/docs/reference/config/#main-name) and can be any lowercase domain name, such as `local.myapp.com`, but not a wildcard, `localhost` or an IP address. A real domain asks for approval, which typing it here gives. One that comes from the project’s [`.nearhostrc`](/pr-preview/pr-96/docs/reference/nearhostrc/) is asked about on the last step. The hints under the name and alias need Nearhost 0.8.0 or later. 6. **Confirm.** The server, path, address and routes, with any advice. It also lists anything that needs approval, such as a host or option from the project’s `.nearhostrc`, and `enter` approves it as it adds the project. The project is selected and starts at once. If its alias is not in `/etc/hosts` yet, Nearhost asks for your password to add it. See [First run](/pr-preview/pr-96/docs/getting-started/first-run/#the-password-box). ## Typing a path Nearhost suggests directories as you type, on this machine and on servers alike. It reads each folder in the background, so typing never waits. 
```text
path      ~/code/bl▏og/
          blog  blob
```
 The rest of the suggested name appears faint after the cursor. When several directories match, they are listed under the field. | Key | Action | | ---------- | ------------------------------------------------------- | | `tab`, `→` | Accept the suggestion. | | `↑`, `↓` | Choose between the matches. | | `enter` | Use the path exactly as typed, without the suggestion. | | `ctrl+r` | Reconnect to the server, if the connection has dropped. | `tab` with nothing suggested lists the folder again, which picks up a directory made since. Hidden directories are suggested once you type the `.`. ## From the command line `nearhost add` takes a path and discovers its routes the same way. Run without a terminal, as in a script, it prints: 
```text
$ nearhost add --server mini '~/code/myapp' --web 8080
No preset registries are trusted. To use the official presets: nearhost preset registry add nearhost/presets


Routes found for myapp (mini:/home/dev/code/myapp):
  PORT  ROLE    LABEL
  3307  ignore  forward-db (FORWARD_DB_PORT)
  5174  ignore  vite (VITE_PORT)
  8080  web     app (APP_PORT)


Added myapp on mini at https://myapp.test
Start it with `nearhost up`.
```
 With no registry trusted, only the `.env` port variables are found, and every port but the web one is `ignore`. Here the Vite port should reach the browser as `localhost:5174`, so change it to `loopback` afterwards: select the project, press `tab`, choose the route and press `space`. The [Vite and Sail presets](/pr-preview/pr-96/docs/concepts/presets-and-registries/) do that for you. At a terminal it asks what the interface asks: whether to trust the official presets, which suggested presets to enable, and which port is the web app when that is not clear. It also offers to add a server it does not know, and asks you to approve any real domain, wildcard, `localhost` or Docker access that the project’s `.nearhostrc` or presets ask for. Without a terminal it takes the defaults, and stops if it cannot tell which port is web or if something needs approval. See [Approval](/pr-preview/pr-96/docs/reference/nearhostrc/#approval). | Flag | Effect | | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | | `--server <name>` | The server the path is on. The default is `local`. | | `--name <name>` | The project name. The default is the directory’s name. | | `--alias <alias>` | The main name. The default is `<name>.test`. Any lowercase domain name works, but not a wildcard, `localhost` or an IP address. Typing it approves it. | | `--web <port>` | The port to serve at the alias. | | `--host <host>` | Add this host to the primary web route. Repeat for more. Typing it approves it. | | `--preset <name>` | Enable this preset without asking. Repeat for more. | | `--no-presets` | Use no presets and suggest none. | | `--disabled` | Add it disabled: `nearhost up` starts it only when named. | A directory whose name has letters or digits outside ASCII, such as `café`, needs `--name` with only a-z, 0-9 and `-`, or `--alias`, or an `alias` in its `.nearhostrc`. From Nearhost 0.8.0, `nearhost add` stops and says so. A `~` in the path means the server’s home directory, even when your shell has already turned it into this machine’s. ## Route roles | Role | What happens | | ---------- | -------------------------------------------------------------------------------------------------------- | | `web` | Served through the proxy. The first is served at `https://<alias>`, and each later one at its own hosts. | | `loopback` | Raw forward to the same port on your laptop’s `127.0.0.1` and `[::1]`. Skipped for local projects. | | `ignore` | Listed, not forwarded. | Discovery proposes the roles, and you can change them at any time. See [Routes and roles](/pr-preview/pr-96/docs/concepts/routes-and-roles/). A project can have several web routes, each served at hosts of its own. In the form, choose a web route on the routes step and press `h` to type its hosts. On the command line, `--host` adds a host to the primary web route. See [Multi-host projects](/pr-preview/pr-96/docs/concepts/multi-host-projects/). Advisories are shown, never applied. See [Advisories](/pr-preview/pr-96/docs/reference/advisories/). Nothing on the remote machine is edited. ## What gets written Every project lives in `~/.config/nearhost/config.yaml`. You can edit it by hand too. 
```yaml
projects:
  - name: myapp
    server: mini
    path: /home/dev/code/myapp
    alias: myapp.test
    enabled: true
    routes:
      - { port: 3307, role: ignore, label: 'forward-db (FORWARD_DB_PORT)' }
      - { port: 5174, role: loopback, label: 'vite (VITE_PORT)' }
      - { port: 8080, role: web, label: 'app (APP_PORT)' }
```
 See [config.yaml](/pr-preview/pr-96/docs/reference/config/) for every key.

# Coding agents

> Let Claude Code, Codex or another coding agent add projects, open browser previews and show documents through Nearhost, on this machine or on a server, with your approval.

A coding agent can ask Nearhost to add the project it is working in, can read whether a project is served and where, and can find and fix what stops it being served. It works the same when the agent runs on your laptop or on a server Nearhost is connected to, for example in an SSH session. The agent proposes and you decide: every add opens the add form in Nearhost, filled in, for you to save or dismiss. * [Add a project](/pr-preview/pr-96/docs/coding-agents/add-a-project/): the agent proposes the project, and Nearhost opens the add form, filled in, for you to save. * [Fix a project](/pr-preview/pr-96/docs/coding-agents/fix-a-project/): the agent runs Nearhost’s checks on the project and fixes what it can, with your agreement. * [Browser previews from a server](/pr-preview/pr-96/docs/coding-agents/browser-previews/): the agent asks to forward its dev server’s port, and the preview opens in your laptop’s browser. * [Documents from coding agents](/pr-preview/pr-96/docs/coding-agents/documents/): the agent asks to show a plan, spec or mockup it wrote, and Nearhost opens it in your browser. An add waits for your yes in Nearhost. A browser preview or a document asks first too, unless you chose Always allow for it. See [Prompts and Always allow](/pr-preview/pr-96/docs/coding-agents/prompts-and-always-allow/). ## Install the skill The `nearhost` skill installs with the [skills](https://skills.sh) CLI, which puts it where your agents look for skills: Claude Code, Codex, Cursor, Gemini CLI, GitHub Copilot and many more. 
```sh
npx skills add nearhost/nearhost -g
```
 `-g` installs it for your user rather than into the current project. Add `-a codex`, `-a cursor` and so on to choose the agents; without it, the CLI asks. Install it where the agent runs: on the laptop, on the server, or both. In Claude Code you can install it as a plugin instead: 
```text
/plugin install nearhost --marketplace nearhost/nearhost
```
 The skill needs `sh` and `curl`, and nothing else. Nothing is installed with it. The plugin also brings a `SessionEnd` hook, which closes browser previews when the session ends.

# Add a project from an agent

> Ask a coding agent to add the project it is working in, then save or dismiss the add form Nearhost fills in.

With the [`nearhost` skill installed](/pr-preview/pr-96/docs/coding-agents/#install-the-skill), ask your coding agent to serve the project it is working in, and Nearhost opens the add form for you to review. In the project’s directory, run `/nearhost add` in Claude Code, or `$nearhost add` in Codex. Asking in your own words, such as “serve this with Nearhost”, works too. 1. The agent proposes the project’s directory to Nearhost, with the dev server’s port when the project’s files say it plainly. 2. Nearhost notifies the terminal it runs in: `Agent on mini wants to add /home/dev/code/myapp`. Most terminals show it only when Nearhost is not the window or tab in front. 3. The add form opens over the view with the server and path filled in, and the line `Proposed by an agent on mini`. Nearhost reads the project as it does for any add, and you choose the routes and the name as usual. 4. Save it, and the agent reports `https://myapp.test`. Press `esc` on the path, and the agent is told you declined. 5. The agent waits up to 30 seconds for the project to start, then runs the doctor on it and offers to work through any errors or warnings it finds. See [Fix a project](/pr-preview/pr-96/docs/coding-agents/fix-a-project/). If a form is already open, the proposal waits, and Home shows `1 request waiting · p to review`. It opens when the form closes, or when you press `p`. An agent waits 10 minutes for an answer. `/nearhost status` reports the project holding the current directory: its address, every address it serves in `urls`, its state and any error. A project with several web routes or hosts has one URL for each, so you can see where each service lives. `/nearhost status --all` reports every project on the machine the agent runs on. Proposals need the full-screen interface. Under `nearhost up`, an agent can read the status but is told to open `nearhost` to propose.

# Browser previews from a server

> Let a coding agent on a server open its dev server's preview in your laptop's browser, after you allow it in Nearhost.

With the [`nearhost` skill installed](/pr-preview/pr-96/docs/coding-agents/#install-the-skill), an agent on a server can start a dev server, but you cannot see it in your browser until its port is forwarded to your laptop. With a passthrough, the agent asks Nearhost to forward that one port for the rest of the session, and you approve it first. The preview then opens on your laptop. It works for any HTTP dev server, whatever it is built with, as long as the page loads everything from that one port. Needs Nearhost 0.10.0 or later; an older Nearhost answers without passthrough, and the agent tells you to update it. 1. The agent asks for a port, and Nearhost opens a prompt over the interface: `Claude Code on mini wants to open port 5173 on this laptop (browser preview).` If that port is in use on the laptop, the prompt says so and that it will open on another port; the agent reports the laptop URL once it opens. 2. Answer the prompt. See [Prompts and Always allow](/pr-preview/pr-96/docs/coding-agents/prompts-and-always-allow/#the-prompt) for the keys, and [Always allow](/pr-preview/pr-96/docs/coding-agents/prompts-and-always-allow/#always-allow) to stop being asked. If you allow it and the port cannot be opened, the prompt shows why, and the agent is told it failed rather than that you refused, so it passes the reason on. If the port opens but Always allow cannot be saved, the passthrough stays open and the log says Always allow was not saved. If the request has ended by then, because it expired or the agent’s session ended, pressing `y` or `a` tells you so; `n` or `esc` closes the prompt. 3. Once you allow it, Nearhost forwards the port and the agent gives you the laptop URL. Asking again for a port that is already open, from the same agent session, returns the same passthrough without a second prompt. A port that a running project already forwards is answered at once, with no prompt. On a server’s panel, press `tab` to move to the server’s open passthroughs, which are shown only when there are any. When there are more than fit, they scroll with the selection, and a `+N more` line says how many are hidden above or below. Use `j` and `k` or the arrow keys to move, and `tab` or `esc` to leave. Press `x` on a passthrough to close it at once. Home shows a `passthroughs` count while any are open. ## When a passthrough ends A passthrough ends when any of these happens: * the session ends, which Claude Code’s `SessionEnd` hook reports; * you disconnect the server in Nearhost, remove it, or its connection fails (for example, authentication); * the server has been away for 10 minutes in a row; * the forwarded port stops answering for 5 minutes, checked every 30 seconds while the server is connected; * you close it, or Nearhost quits. The `SessionEnd` hook ships with the Claude Code plugin, so it runs only for plugin installs. With the skill installed through the skills CLI, or in another agent, the other conditions apply. If the laptop port was taken by something else while the server was away, that passthrough closes when the server comes back. If closing a passthrough’s forward fails, Nearhost keeps its laptop port and tries again on each check until it closes. ## Without Nearhost connected When Nearhost is not connected to the server, the agent cannot ask for a passthrough. It tells you to select the server in Nearhost and press `c`, then ask again, or to forward the port yourself from the laptop. Adding `-o ExitOnForwardFailure=yes` to the command it gives makes `ssh` stop with an error when the laptop port is already taken, rather than stay connected without the forward: 
```sh
ssh -N -o ExitOnForwardFailure=yes -L <port>:localhost:<port> <server>
```

# Documents from coding agents

> Let a coding agent show a plan, spec or mockup it wrote in your laptop's browser, after you allow it in Nearhost.

With the [`nearhost` skill installed](/pr-preview/pr-96/docs/coding-agents/#install-the-skill), when an agent writes a plan, spec, report or HTML mockup for you to read, it can ask Nearhost to show it. Nearhost serves the document at an address on your laptop and opens it in your browser. This works for an agent on the laptop and for one on a server Nearhost is connected to, so you no longer need a second terminal to read a path on a server. Markdown is shown as a page; HTML is served as written. Agents offer this only for documents they wrote for you, never for code or config files. You can also ask directly with `/nearhost open <path>` in Claude Code, or `$nearhost open <path>` in Codex. Needs Nearhost 0.11.0 or later; an older one answers without them, and the agent tells you to update it. 1. The agent asks, and Nearhost opens a prompt over the interface: `Claude Code on mini wants to show plans/2026-10-28-x.md`, with a line saying which folder Nearhost will serve. 2. Answer the prompt. See [Prompts and Always allow](/pr-preview/pr-96/docs/coding-agents/prompts-and-always-allow/#the-prompt) for the keys, and [Always allow](/pr-preview/pr-96/docs/coding-agents/prompts-and-always-allow/#always-allow) to stop being asked. If you refuse, the agent does not offer that folder again in the session and only gives you the path. 3. Once you allow it, your browser opens the document and the agent gives you the address. It looks like `https://localhost:<web port>/d/<random>/plans/2026-10-28-x.md`, where `<web port>` is Nearhost’s web port, and `<random>` is a long random string that other pages cannot guess. With Always allow, the document opens in your browser at once, and Nearhost shows `Claude Code on mini opened plans/2026-10-28-x.md` in the status line. ## What is served Nearhost serves the document’s git repository, so its images, stylesheets and linked documents work. A document that is not in a repository serves its own folder. A repository at your home folder, or above it, is never served whole: Nearhost serves the document’s own folder instead. A document directly in your home folder, or in `/`, is refused with `save the document in a project or a folder of its own`. Nearhost never serves dotfiles or the contents of dot folders inside that folder, and never follows a link out of it. A second document in the same folder reuses the address without a prompt for the agent you approved, and prompts any other. Nearhost keeps no copies. Each time the page loads, it reads the file again, from the laptop or over the server’s SSH connection, so reloading shows the current file. A file that has moved or gone shows as missing, never as an old version. A server that is not connected shows a page saying so; select it in Nearhost and press `c`. ## Documents cannot reach your other pages Every file Nearhost serves from a document’s folder is sandboxed by the browser. Its scripts run, but they cannot read other pages on `localhost`, your projects’ cookies or storage, or other documents. Rendered markdown runs no scripts at all. Pages also send no referrer, so the address does not leak to sites a document links to. ## When a served folder goes away Nearhost lists served folders on each server’s panel; press `tab` to reach its `documents` section. Home shows a count in its `agents` line. A folder stays served until: * Nearhost quits, as nothing is saved across restarts; * you press `x` on it in the server’s panel and confirm; * you remove the server from Nearhost, or rename it. Disconnecting a server does not remove its folders. Their pages say the server is not connected until it reconnects. The agent’s session ending does not remove them either, so you can read yesterday’s plan again while Nearhost runs. Home’s web page also lists the folders served since Nearhost started, with links to each document. If Nearhost has no web port, because `--web-port 0` turned it off or the port was taken, and a project holds `localhost`, there is no page to serve from, and the agent is told so.

# Fix a project

> Let a coding agent run Nearhost's project checks and fix what stops the project being served.

With the [`nearhost` skill installed](/pr-preview/pr-96/docs/coding-agents/#install-the-skill), ask your coding agent to find and fix what stops a project being served. When a project is not served as you expect, run `/nearhost doctor` in its directory, or `$nearhost doctor` in Codex. The agent asks Nearhost to run the same [project checks](/pr-preview/pr-96/docs/reference/cli/#project-checks) as `nearhost doctor` on this project, and works through the errors, then the warnings. Unlike `nearhost doctor`, this first reads the project’s `.nearhostrc` again, as described under [Agent API](/pr-preview/pr-96/docs/coding-agents/how-it-works/#agent-api). Each finding’s fix has a kind, and the agent handles each kind in its own way: * **`project`.** The agent shows you the change, the snippet and where it goes, and makes it in the project’s files once you agree. When the setup is more than Nearhost can work out for itself, such as several hosts, a pattern, `localhost` or callbacks from Docker, it writes or edits the project’s [`.nearhostrc`](/pr-preview/pr-96/docs/reference/nearhostrc/). * **`nearhost`.** Something you do in Nearhost, such as adding a port in the edit form. The agent passes it on, or offers to write the port or host into `.nearhostrc` instead. * **`manual`.** Something only you can do, such as a DNS record. The agent tells you what it says. After editing `.nearhostrc`, and for `nearhostrc.pending` and `nearhostrc.not-applied`, the agent asks Nearhost to read the file again. A change that needs no approval applies at once. One that needs it waits, and the agent tells you to approve it in Nearhost, then waits for your answer. See [Approval](/pr-preview/pr-96/docs/reference/nearhostrc/#approval). Then it runs the doctor again, and stops when nothing is left that it can fix. It never edits Nearhost’s `config.yaml` itself; Nearhost saves a change there when it applies one. Approving a change needs the full-screen interface: under `nearhost up`, the agent tells you to open `nearhost`.

# How agents reach Nearhost

> The socket a coding agent reaches Nearhost on, how Nearhost forwards it to each server, and the agent API.

This page explains the socket an agent talks to Nearhost on, and the calls it makes. Nearhost listens on `~/.nearhost/<id>.sock` on your laptop, where `<id>` is six letters and digits made when Nearhost first runs and kept in `~/.config/nearhost/id` with a fingerprint of the machine. A config directory copied to another machine gets a new id there, so two laptops never share a socket. On each server it is connected to, it forwards a socket of the same name over its own SSH connection: 
```sh
ssh -S <sock> -O forward -R <home on the server>/.nearhost/<id>.sock:<socket on the laptop> -- <host>
```
 A request is answered for the machine its socket belongs to, so an agent on `mini` sees and proposes only projects on `mini`. sshd creates the socket readable by your account only. A socket path can be at most 103 bytes on macOS and 107 on Linux. With a home directory long enough to pass that, agents can’t reach Nearhost. From Nearhost 0.8.0, its log says `socket path is too long`. * **The one change on a server.** Nearhost creates `~/.nearhost` there, private to your account, and removes its own socket from an earlier run before forwarding again. sshd leaves the socket behind when the connection ends; the skill skips sockets that do not answer. * **Two laptops on one account.** Each install has its own id and socket, so both work. When more than one answers, the agent asks which laptop you mean. * **A server with no tunnel.** The forward exists while Nearhost is connected to the server, which is from when one of its projects starts, or when you select the server and press `c`. Otherwise the agent says to start Nearhost and connect the server, or gives the `nearhost add --server` command to run on the laptop for a server Nearhost does not know yet. * **A server that is this machine.** A server whose home is the laptop’s own, such as `ssh_host: localhost` on your account, gets no forward: agents there already reach Nearhost on the laptop’s socket. Nearhost tells this from another machine whose home has the same path, such as a second Mac with the same user name, by checking whether the server sees a file it has just made on the laptop. That machine gets its forward like any other. To use one socket explicitly, set `NEARHOST_SOCKET` to its path where the agent runs. ## Agent API The skill’s script talks to Nearhost over that socket, with `curl --unix-socket`. Nearhost answers JSON for the machine the socket belongs to. These calls are the ones the doctor uses: * `GET /v1` says which API this is. Its `capabilities` list names the calls added since the first release of API 1: `doctor`, `reload`, `passthrough` and `documents`. An older Nearhost leaves them out, and the skill tells you to update it. When passthroughs are available it also gives `id`, the laptop’s install id, which the skill uses to keep a token per laptop. * `GET /v1/doctor?path=…` returns `project` and `findings` for the project holding the absolute path, in the shape that [`nearhost doctor --json`](/pr-preview/pr-96/docs/reference/cli/#json-output) gives its findings. For a project already in Nearhost, it first reads the project’s `.nearhostrc` again, as a reload does: a change that needs no approval is applied, restarting the project if it runs under `nearhost up`, and one that needs approval waits in Nearhost. For a directory that is not in Nearhost yet, `project` is `null`, each finding’s `project` is empty, and the findings are for the project as it would be added. * `POST /v1/projects/reload`, with `{"path": "/abs/dir"}`, asks Nearhost to read the `.nearhostrc` of the project holding the path again. The project must be added first. It answers `applied` when nothing needs approval, or `pending` with an `id` the agent waits on, as it does for a proposal, while you decide. A change you declined stays declined until the file changes or Nearhost restarts.

# Prompts and Always allow

> How Nearhost asks before an agent opens a preview or a document, what Always allow covers, and how to revoke it.

Browser previews and documents ask you first, in the same way. This page covers the prompt, what Always allow does, and how to take it back. ## The prompt Press `y` to allow it, `n` to refuse, or `a` for Always allow. `esc` counts as No. A prompt that waits 10 minutes expires. The prompt queues with proposals and passthroughs, and Home shows the same hint as for a [proposal](/pr-preview/pr-96/docs/coding-agents/add-a-project/). ## Always allow Always allow covers one tool on one server: Claude Code on `mini`, say, but not Claude Code on another server, and not another tool on `mini`. Only Claude Code is offered it. Codex documents no variable that identifies it, so Codex and every other agent are shown as `An agent`, are always prompted and are never offered Always allow. Previews and documents are approved separately, so revoking one leaves the other working. To revoke one, press `tab` on the server’s panel to reach its `always allowed` section, and `x` on a row. Nearhost asks you to confirm first. Revoking leaves open passthroughs and documents in place. ## What the token protects When you choose Always allow, Nearhost makes a token for that tool on that server. The skill keeps the token on the server, in `${XDG_STATE_HOME:-~/.local/state}/nearhost/tokens/<laptop id>/<requester>`, readable by your account only. For documents, the file ends in `.documents`, beside the preview token. The skill sends it with later requests, so Nearhost does not ask again. The laptop keeps only a SHA-256 hash of the token, in `grants.json` beside the install id in `~/.config/nearhost` (or under `XDG_CONFIG_HOME`). The token stops a different tool from borrowing an approval, and it stops anything from using one after you revoke it. It does not protect against anything else running as your account on the server: such a process can read the token file and use the approval. Treat Always allow as trust in everything that runs as you on that server. A wrong or revoked token gets a `401`; the skill drops it and asks again, so you are prompted. Removing a server from Nearhost, or renaming it, revokes its Always allow grants, so a server added later under the same name starts with none. Nearhost does this when it next applies the config or starts, and the log says how many it removed. It does this only for its default config file, not one given with `--config`, and never while that file is missing, so a config file that disappears for a moment does not cost you your grants. If `grants.json` cannot be read, Nearhost still serves coding agents but turns passthrough off, and says which file it could not read. Fix or remove the file, then restart Nearhost. ## Turn notifications off Nearhost notifies the terminal when an agent asks to add a project, open a preview or show a document. To stop that, add this to the [config](/pr-preview/pr-96/docs/reference/config/). The prompts still open in Nearhost: 
```yaml
notifications: false
```

# When agents cannot reach Nearhost

> Fix an sshd that refuses Nearhost's socket forward, or an agent sandbox that blocks the socket.

Two things can stop an agent reaching Nearhost: the server’s sshd, or the agent’s own sandbox. **The server refuses the forward.** Its sshd has `AllowStreamLocalForwarding no`. The server’s panel shows `agents unavailable` with sshd’s message, and so does `nearhost doctor`. Set `AllowStreamLocalForwarding yes` in the server’s `sshd_config`, reload sshd and press `r` on the server to reconnect. Projects serve either way, and `r` on Home leaves such a server connected. **The agent’s sandbox blocks the socket.** Agents that run commands in a sandbox block Unix sockets by default, so the skill’s script cannot reach `~/.nearhost`. Allow only what Nearhost needs. * **Approve the one command.** Claude Code and Codex ask before they run a command the sandbox blocks outside it. Approving that for the skill’s script opens nothing else, so it is the narrowest choice. * **Claude Code on macOS** can allow the one socket by its full path, which `ls ~/.nearhost` shows, in `~/.claude/settings.json` where the agent runs: 
  ```json
  { "sandbox": { "network": { "allowUnixSockets": ["/Users/dev/.nearhost/k3f9q2.sock"] } } }
  ```
 Two settings also work, but open far more than Nearhost: * **Claude Code on Linux** cannot allow one socket, only every one, with `"allowAllUnixSockets": true`. * **Codex’s** `network_access = true` under `[sandbox_workspace_write]` gives its sandbox the network and every socket. Every socket includes ones like Docker’s `/var/run/docker.sock`, and a command that reaches Docker’s socket can take over the machine. Use these settings only if that is acceptable where the agent runs; otherwise approve the command when the agent asks.

# Dev servers and hot reload

> How assets and live reload reach your browser, and when a project needs a loopback forward.

A page served from `https://<alias>` usually needs a second thing to work: the dev server that builds its scripts and pushes live updates. There are two ways that server shows up, and Nearhost handles both. ## The dev server is the web app A Vite, Next.js or similar project serves pages and assets from one port. Give that port the `web` role and you are done. Hot reload uses a WebSocket on the same origin, and the proxy passes WebSocket upgrades through. Vite checks the `Host` header, so it needs the alias in `server.allowedHosts`. With the `nearhost/vite` preset enabled, Nearhost shows the exact lines to add. See [Advisories](/pr-preview/pr-96/docs/reference/advisories/). ## The dev server sits beside a backend A backend framework renders the HTML, and the page loads its scripts from a separate dev server at an address like `http://localhost:5173`. Rails, Django and Laravel projects that use Vite all work this way. That address is resolved by your browser, on your laptop. Nothing listens there, so scripts fail to load and hot reload never connects. A `loopback` route fixes it. Nearhost forwards the same port number on your laptop to the dev server on the remote machine, so `localhost:5173` in the browser reaches port 5173 over there. The remote project needs no changes, as long as the page asks for `localhost`. A Laravel project outside Sail whose Vite listens on `::1` writes `http://[::1]:5173` to `public/hot`. The forward answers on both `127.0.0.1` and `[::1]`, so the page reaches the dev server either way. ### Vite on `[::1]` The forward answers on `[::1]` from Nearhost 0.7.0, on a laptop with the IPv6 loopback. Run `nearhost update` to get it. See [CLI](/pr-preview/pr-96/docs/reference/cli/#nearhost-update). With an older Nearhost, or on a laptop with IPv6 turned off, the forward answers on `127.0.0.1` only, and nothing answers `http://[::1]:5173`. Set `server.hmr.host` to `'localhost'` in `vite.config.js` and restart `npm run dev`, so that `public/hot` says `localhost` instead: 
```js
export default defineConfig({
  // The rest of the config stays as it is.
  server: {
    hmr: { host: 'localhost' },
  },
});
```
 Discovery proposes a loopback route only under Laravel Sail. For other backends, select the project, press `tab`, choose the dev server’s route and press `space` to make it `loopback`. See [Routes and roles](/pr-preview/pr-96/docs/concepts/routes-and-roles/#changing-roles). To see which forwards plain `ssh -L` would need for the same project, see [Vite hot reload fails over SSH port forwarding](/pr-preview/pr-96/docs/guides/vite-hot-reload-over-ssh/). ## What happens when a project starts 1. For a project on a server, Nearhost waits for its SSH connection. If the server cannot connect, the project does not start. 2. The hosts block is checked. It holds `127.0.0.1 <alias>` and `::1 <alias>` for every `.test` project, and for an enabled project with another [main name](/pr-preview/pr-96/docs/reference/config/#main-name) unless DNS already sends that name only to loopback. An enabled project’s exact web hosts are listed the same way. Nearhost asks for your password only if it needs to change. 3. For a project on a server, one `-L` forward is added per `web` route, each on an ephemeral local port, and one per `loopback` route, on the same port locally. A local project needs no forwards. 4. The proxy rebuilds its Caddy config with the new site and applies it in-process. 5. The project’s state becomes `running`. A request to `https://myapp.test` reaches Caddy on 443, then the ephemeral local port, then the web port on the remote. A script tag pointing at `http://localhost:5173/...` reaches the loopback forward on 5173, then port 5173 on the remote. The hot reload client connects to the origin its script came from, so it works with no remote configuration. ## Example: Laravel Sail Under Sail, `laravel-vite-plugin` writes `public/hot` as `http://localhost:<VITE_PORT>`. With the official presets trusted and `nearhost/sail` enabled, discovery reads the Compose file, makes the port published for container port 80 the `web` route, and proposes `VITE_PORT` as a `loopback` route. A Sail project then needs no manual setup. See [Presets and registries](/pr-preview/pr-96/docs/concepts/presets-and-registries/). ## Running several projects at once A loopback route uses the same port number on both machines, so two running projects cannot share one. Give each project’s dev server its own port. Nearhost warns you before the clash happens, and suggests a free port when the port comes from a variable. Adding a clashing project is refused unless you add it with `--disabled`. See [Advisories](/pr-preview/pr-96/docs/reference/advisories/). If another program already holds the port on your laptop, the project goes into `error` and names the program. Its other routes still start. ## Reloads and reconnects Starting or stopping a project reloads the proxy without closing open WebSockets, so hot reload in other tabs stays connected. If the SSH connection drops, Nearhost reconnects and puts every forward back. The project shows `degraded` meanwhile.

# Discovery

> How Nearhost reads a project's files to propose routes without running anything.

Discovery takes a server and a path, reads the project’s files and proposes routes with labels and roles, plus advisories. It saves typing. It is not a requirement: a project it knows nothing about works once you give its web port. Discovery only reads. No command runs on the remote machine. On a server the files are read over SFTP, through an SSH connection of discovery’s own. On `local` they are read from disk. ## The .env rule Without presets, Nearhost reads `.env`, then `.env.local`, and the later file wins. A port variable is any variable with `PORT` or `PORTS` as one of its parts, split on `_` or `-`, whose value is a whole number from 1 to 65535. `APP_PORT`, `FORWARD_DB_PORT` and `vite-port` all count. Each one becomes a route labelled with the rest of its name and the variable itself: 
```text
  8080  app (APP_PORT)
  3307  forward-db (FORWARD_DB_PORT)
```
 When several variables hold the same port, the first in alphabetical order names it and the others are added in brackets. With no registry trusted, this is all discovery does, and it makes no network request. ## What presets add Each enabled preset that applies to the project adds to what is found. See [Presets and registries](/pr-preview/pr-96/docs/concepts/presets-and-registries/). * **Compose files.** A preset that asks for Compose ports, such as `nearhost/compose` or `nearhost/sail`, makes discovery read the first of `docker-compose.yml`, `docker-compose.yaml`, `compose.yml` and `compose.yaml`. Each published TCP port becomes a route, labelled with its service, or `service (VAR)` when a variable sets it. `${VAR}`, `${VAR:-default}`, `${VAR-default}` and `$VAR` are filled in from the `.env` files, never from your shell. Ranges, UDP ports and ports that are not published are skipped. Without such a preset the Compose file is not read, and Nearhost says so. * **Other files.** A preset can scan files such as `vite.config.ts` for values with a regular expression, and check `package.json` for a dependency. Nothing is executed, and JavaScript is not parsed. * **Labels and roles.** A preset can relabel a port variable, propose a route as `loopback`, and hint which port should be the web route. * **Advice.** Most advisories come from presets. See [Advisories](/pr-preview/pr-96/docs/reference/advisories/). ## Who claims a port Each port is claimed once, by the first source that finds it: 1. Compose’s published ports, when a preset asked for them. 2. Each preset that applies, in the order they declare. 3. The `.env` rule, for ports nothing else claimed. A later preset can replace an earlier one’s route or advice by using the same id, or remove it. ## Roles Every proposed route starts as `ignore`, unless a preset proposes `loopback`. Then one route is made `web`, in this order: 1. A route a preset prefers as the web route. 2. A Compose port whose container port is 80. 3. A route a preset offers as a fallback, such as Vite’s configured port. 4. The only route, when no preset recognised the project. If none of these applies, the interface asks you for the web port, and `nearhost add` asks at a terminal or needs `--web <port>`. See [Routes and roles](/pr-preview/pr-96/docs/concepts/routes-and-roles/). ## When something cannot be read A file that does not exist is skipped. A file that exists but cannot be read stops discovery with its error, rather than being treated as absent. If nothing at all is found, the interface asks for the web port.

# Multi-host projects

> How one project serves several web routes, each at hosts of its own, and where those hosts come from.

A project can serve more than one name. An app, its WebSocket server and its file store can each answer at a host of their own, all from one project in Nearhost. ## Several web routes A project can have several `web` routes. The first is the primary: it is served at the project’s [main name](/pr-preview/pr-96/docs/reference/config/#main-name), and at any hosts you give it too. Every other web route is served only at its own hosts, so it needs at least one. You give a route hosts in three ways: * **In the interface.** On the routes step of the add or edit form, choose a web route and press `h`. Type its hosts separated by spaces, and press `enter`. * **On the command line.** `nearhost add --host <host>` adds a host to the primary web route. Repeat it for more. * **In the project’s files.** A [`.nearhostrc`](/pr-preview/pr-96/docs/reference/nearhostrc/#keys) lists hosts for each route, and presets can find them in `.env`. See [Hosts from presets](#hosts-from-presets). In the routes view on the main screen, `w` makes a route web. If it has no hosts, it becomes the primary. Other web routes with no hosts become `ignore`, so a route with hosts of its own keeps serving them. ## Host patterns A host is an exact name, such as `api.local.example.com`, or a pattern with `*` in place of one label, such as `*.status.local.example.com`. * `*` stands for exactly one label. `*.status.local.example.com` matches `eu.status.local.example.com`, but not `status.local.example.com` or `a.eu.status.local.example.com`. * `*` can be the leftmost label or one in the middle, as in `internal.*.local.example.com`. * The part to the right of the last `*` must be at least two labels, and more than a public suffix. A pattern that is only wildcards is refused, and so are `*.test`, `*.com` and `*.co.uk`. `*.myapp.test` is allowed. * `localhost` is allowed as an exact host. Any other name needs at least two labels, and an IP address is refused. * Hosts are lowercase. ## Which route answers When several hosts match a name, the most specific one answers: 1. An exact host beats any pattern. 2. Among patterns, the one with more fixed labels wins, so `internal.*.local.example.com` beats `*.*.local.example.com`. 3. Patterns with as many fixed labels are taken in lexical order. A host can be served by only one enabled project. Two exact hosts clash when they are the same name, and two patterns when they are written the same. An exact host under another project’s pattern does not clash, because the exact host wins. Saving an enabled project, or starting one, that would serve a host another enabled project serves is refused with `host <host> is already served by project "<other>"`. `nearhost doctor` warns, as `hosts.overlap`, when a pattern overlaps another project’s without being the same. ## Certificates and DNS Each exact host gets its own certificate. A name under a pattern gets one the first time it is visited. See [TLS and the proxy](/pr-preview/pr-96/docs/concepts/tls-and-the-proxy/#per-name-certificates). An exact host goes in the hosts file while its project is enabled. One that does not end in `.test` is left out when DNS already points it only at loopback addresses, and `localhost` is never added. Patterns never go in the hosts file, because the file cannot hold them, so a pattern’s names need DNS that points them at this machine. `nearhost doctor` reports a pattern that does not resolve here as `hosts.unresolved-pattern`. See [The hosts file](/pr-preview/pr-96/docs/concepts/the-hosts-file/). ## What needs approval A host that does not end in `.test`, any pattern and `localhost` wait for your approval before they are served. A host you type with `--host` or `h` is approved by typing it. See [Approval](/pr-preview/pr-96/docs/reference/nearhostrc/#approval). ## Hosts from presets A preset can name hosts as well as ports. The [`nearhost/sail`](/pr-preview/pr-96/docs/concepts/presets-and-registries/#the-official-presets) preset reads them from `.env`: | Variable | Served on the port in | | --------------------------------- | ------------------------------ | | `APP_URL` | `APP_PORT`, or 80 | | `REVERB_HOST` | `FORWARD_REVERB_PORT`, or 8080 | | `FILES_URL`, `MINIO_URL`, or both | `FORWARD_MINIO_PORT`, or 9000 | Only the host is taken from each value. A port in the URL is ignored, and the route’s port comes from the variable beside it. The Reverb and MinIO hosts are read only when their port variable is set in `.env` or named in the Compose file. * Inference never proposes `localhost`, an IP address or a name without a dot. A malformed name is left out with a warning. * A route that has inferred hosts becomes a web route. A `loopback` route cannot have hosts, so they are dropped with a warning. * A `.nearhostrc` that lists a route wins over the hosts presets found for it. See [Keys](/pr-preview/pr-96/docs/reference/nearhostrc/#keys). * `nearhost add` leaves out an inferred host that another enabled project already serves, with a note: `Not serving <host>: project "<other>" already serves it.` A later web route left with no hosts becomes `ignore`. A project added with `--disabled` keeps them, since it serves nothing yet. The interface does not leave them out: it refuses to save, and you remove the host with `h`. Inferred hosts are fixed when the project is added or edited. Changing `APP_URL` later does not change what is served. Editing the project, with `e` in the interface, adds any newly inferred hosts to a saved web route and never removes a saved one. `nearhost doctor` reports a host the project’s settings name that no web route serves, as `routes.unserved-host`, and tells you to edit the project. ## Where the URLs show The project view in the interface lists every URL under the project’s name. A pattern is shown dim, since a browser cannot open it. For a coding agent, `/nearhost status` reports the main URL as `url`, and every URL the project serves, the main one first, as `urls`. See [Add a project from an agent](/pr-preview/pr-96/docs/coding-agents/add-a-project/). ## An example A Sail project with an app, Reverb and MinIO, whose Compose file publishes `APP_PORT`, `FORWARD_REVERB_PORT` and `FORWARD_MINIO_PORT`, has this in its `.env`: 
```ini
APP_URL=https://shop.local.example.com
APP_PORT=8010
REVERB_HOST=ws.shop.local.example.com
FORWARD_REVERB_PORT=8090
FILES_URL=https://files.shop.local.example.com:9010
FORWARD_MINIO_PORT=9010
```
 With `nearhost/sail` enabled, `nearhost add` asks you to approve the three hosts, since none ends in `.test`. Nearhost then serves: | URL | Port | | -------------------------------------- | ---- | | `https://shop.test` | 8010 | | `https://shop.local.example.com` | 8010 | | `https://ws.shop.local.example.com` | 8090 | | `https://files.shop.local.example.com` | 9010 | `shop.test` is the main name, so it is served on the primary route with the app’s own host. Add the project with `--alias shop.local.example.com` to make the real name the main one.

# Presets and registries

> How Nearhost learns what a framework's ports mean, and where that knowledge comes from.

On its own, Nearhost knows one thing about a project: the port variables in its `.env` files. Everything it knows about a particular tool, such as Docker Compose, Vite or Laravel Sail, comes from a preset. Presets come from registries, and Nearhost trusts none until you say so. ## What a preset is A preset is a small YAML file that says when it applies, which ports to propose and how to label them, and what advice to give. It is data, not code: * It reads files inside the project. It cannot run a command, make a request or change a file. * Its expressions are [CEL](https://cel.dev) with a cost limit, and its patterns are RE2, which runs in linear time. * A preset that fails to load is skipped with a warning. It never stops a command. Presets combine. On a Sail project with a Vite frontend, `sail`, `laravel` and `vite` all apply, and `sail` changes what `vite` would advise for a dev server that runs in a container. ## The official presets The official registry is [nearhost/presets](https://github.com/nearhost/presets). | Preset | Turns on when | What it adds | | ------------------ | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `nearhost/compose` | The project has a Compose file | A route for every TCP port the Compose file publishes, labelled with its service. A service on container port 80 becomes the web route. | | `nearhost/laravel` | The project has an `artisan` file | Advice when `APP_URL` is not one of the project’s addresses, with `https` and no port, since generated links use it. | | `nearhost/sail` | The Compose file mentions `laravel/sail`, a `sail-` image or `LARAVEL_SAIL` | Compose’s published ports, with the Vite dev server forwarded to `localhost` through `VITE_PORT`. The hosts in `APP_URL`, `REVERB_HOST` and `FILES_URL`, `MINIO_URL`, or both, served on their ports. Vite advice that fits a container. | | `nearhost/vite` | A `vite.config.*` file exists, or `package.json` depends on `vite` | The dev server port from `server.port` as a route. Advice when the port is the default 5173, or when `server.allowedHosts` would reject the alias. | ## Hosts from presets A preset can name hosts as well as ports. `nearhost/sail` reads them from `APP_URL` and `REVERB_HOST`, and from `FILES_URL`, `MINIO_URL` or both, and serves each on its port. The hosts are fixed when you add or edit the project. A project’s `.nearhostrc` wins over them, a real domain among them is asked about first, and `nearhost add` leaves out one that another enabled project serves, with a note. See [Multi-host projects](/pr-preview/pr-96/docs/concepts/multi-host-projects/#hosts-from-presets). ## Trusting a registry A fresh Nearhost trusts no registry and makes no request for presets. The first time you add a project, at a terminal or in the interface, it offers to trust the official registry. Answer yes, no, or don’t ask again. You can also trust it yourself: 
```sh
nearhost preset registry add nearhost/presets
```
 From then on, adding a project suggests the presets that suit it, and asks before enabling each one. In the interface they are listed ticked on the presets step. At a terminal: 
```text
This looks like a Vite project. Enable nearhost/vite from nearhost/presets? [Y/n]
```
 Without a terminal, `nearhost add` prints the `--preset` flag for each suggestion instead, and enables nothing. ## Pinned and checked A registry is a public GitHub repository with an `index.yaml` on its default branch and the presets in `presets/`. The index names a commit and a SHA-256 for every preset. Nearhost downloads each file at that commit and refuses it if its hash differs. * An installed preset never changes until you run `nearhost preset update`. * The index is cached for a day. If a fetch fails, the cached copy is used. * A preset written for a newer Nearhost is refused, with a message to upgrade. Presets from a registry are named after it, as in `nearhost/vite`, so you can see where each one came from. The name before the slash is the registry’s alias, which is the repository owner unless you choose another with `--as`. ## Commands | Command | What it does | | ------------------------------------------- | ----------------------------------------------------------------------------------------- | | `nearhost preset list` | The enabled presets and where they came from, then what each trusted registry offers. | | `nearhost preset enable <name>` | Download, check and enable a registry preset, or enable a local one. | | `nearhost preset disable <name>` | Stop using a preset. Its file is kept. | | `nearhost preset update [name\|registry]` | Move registry presets to the current versions, and say what changed. | | `nearhost preset registry add <owner/repo>` | Trust a registry. `--as <alias>` names it. | | `nearhost preset registry list` | The trusted registries and how old their cached indexes are. | | `nearhost preset registry remove <alias>` | Stop trusting a registry, once none of its presets are enabled. Installed files are kept. | `nearhost add --preset <name>` enables a preset without asking, and `--no-presets` uses none. ## Where they live Presets are files beside the config, under `presets/` in Nearhost’s config folder: `~/.config/nearhost/presets/`, or under `$XDG_CONFIG_HOME/nearhost` when that variable is an absolute path. Each registry’s cached index is beside them, at `registry/<alias>/index.yaml`. One from a registry is `presets/<alias>/<name>.yaml`. A local preset is `presets/<name>.yaml`, with a plain name, and is enabled with `nearhost preset enable <name>`. The config records what is trusted and enabled: 
```yaml
registries:
  - alias: nearhost
    repo: nearhost/presets
presets:
  - name: nearhost/vite
    ref: e6c0be9e14dc89ec5c19bb1bc7d155c1029c298d
    sha256: 024643158cc1d55819e3f62d9d3e429cc8b15dae396cf036db9d573815c9d80e
```
 `registry_prompt: false` stops Nearhost asking about the official registry. Choosing “don’t ask again” sets it. ## Writing your own Write a preset when a framework’s ports or advice are not covered. The [nearhost/presets README](https://github.com/nearhost/presets#writing-a-preset) describes every key and expression. Check a file with `nearhost preset validate <file>`, and test it against sample projects with `nearhost preset test`. Any public GitHub repository laid out like nearhost/presets is a registry. `nearhost preset index` writes its `index.yaml`, and others trust it with `nearhost preset registry add <owner/repo>`. See [Discovery](/pr-preview/pr-96/docs/concepts/discovery/) for how presets and the `.env` rule combine.

# Routes and roles

> How each discovered port becomes a web, loopback or ignored route.

A project has a list of routes. Each route is a port on the server, a role and a label. The role decides what Nearhost does with the port. 
```yaml
routes:
  - port: 8080
    role: web
    label: 'app'
  - port: 5173
    role: loopback
    label: 'Vite (vite.config)'
  - port: 5432
    role: ignore
    label: 'db'
```
 ## web Served through the proxy. A project has at least one. The first is served at `https://<alias>`, and each later one only at hosts of its own, so it needs at least one. Discovery proposes one: a route a preset prefers, then a Compose port mapped to container port 80, then a route a preset offers as a fallback, such as Vite’s configured port, then a project’s only port. See [Discovery](/pr-preview/pr-96/docs/concepts/discovery/#roles). You can move the role to any route. For a project on a server, Nearhost picks an ephemeral local port for the forward and the proxy sends requests for the alias to it. For a local project the proxy sends them straight to the port. ## loopback A raw TCP forward to `127.0.0.1:<port>` on the laptop, using the same port number as the remote. From Nearhost 0.7.0, it answers on `[::1]:<port>` too. Use it for a dev server whose URLs point at `localhost`, such as Vite behind a backend framework. A loopback route means nothing for local projects, because the port is already local, so a local route is either `web` or `ignore`. See [Dev servers and hot reload](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/) for when you need one. ## ignore Discovered and listed, not forwarded. Discovery proposes every route as `ignore` unless it is the web route or a preset proposes `loopback`. In a project’s panel, ignored routes fold into one line with their ports, such as `3 ignored: 3306 6379 1025`. Press `i` to list them, and `i` again to fold them. ## Changing roles In the interface, select the project and press `tab` to move into its routes. Choose a route with `↑` and `↓`, then: * `space` switches it between `loopback` and `ignore` * `w` makes it a web route, the primary if it has no hosts, and other web routes with no hosts become `ignore` Press `tab` or `esc` when you are done. The change is saved and applied at once. `e` on the project reads its files again and walks through the routes step of the form. From the command line, `nearhost add --web <port>` chooses the web route. ## Uniqueness rules * Aliases must be unique across projects, ignoring case. * Loopback ports must be unique across enabled projects. Adding a project whose loopback port another enabled project uses is refused, and a config file with such a clash does not load. * Each project has at least one `web` route. Every web route after the first needs at least one host.

# SSH transport

> How Nearhost drives OpenSSH with one supervised control master per server.

Nearhost shells out to OpenSSH, so your `ssh_config` applies. If `ssh <host>` works without a prompt, Nearhost works. ## One master per server Each remote server gets one OpenSSH ControlMaster process, supervised by Nearhost and started when a project there first needs it: 
```sh
ssh -N -M -S ~/.config/nearhost/run/<server>.sock \
    -o BatchMode=yes -o ExitOnForwardFailure=yes \
    -o ServerAliveInterval=15 -o ServerAliveCountMax=3 \
    -o ControlPersist=no -o ClearAllForwardings=yes \
    -o RemoteCommand=none -- <host>
```
 The control socket is in `run/` in Nearhost’s config folder. The example shows the default, `~/.config/nearhost`; with an absolute `XDG_CONFIG_HOME`, it is `$XDG_CONFIG_HOME/nearhost/run` instead. When the socket’s path would be too long for a Unix socket, it is named `h-<hash>.sock`. The last three options keep the master to Nearhost’s own forwards: `LocalForward` and `RemoteForward` lines in your config are left out, and a `RemoteCommand` is not run. The `local` server needs no transport. Discovery and the add forms open a separate connection of their own, so reading a project’s files never disturbs a running one. ## Forwards added live Forwards are added and removed on the running master, with no reconnect: 
```sh
ssh -S <sock> -O forward -L 127.0.0.1:<local>:localhost:<remote> -- <host>
ssh -S <sock> -O cancel -L 127.0.0.1:<local>:localhost:<remote> -- <host>
```
 The forward always listens on `127.0.0.1`. From Nearhost 0.7.0, a `loopback` route also gets a relay that Nearhost runs on `[::1]:<port>` and passes to that forward, so the port answers on both loopback addresses. On a machine without the IPv6 loopback, it answers on `127.0.0.1` only. A program already listening on `[::1]:<port>` counts as holding the port. [Forward several ports over SSH without retyping -L](/pr-preview/pr-96/docs/guides/forward-ports-over-ssh/) compares this with the ways to do it by hand. Nearhost keeps the list of forwards each server should have. After a reconnect it puts them all back before the server shows as connected. A forward that fails, because something on your laptop holds the port, puts its project in `error` with the name of the program. ## The agent socket Each master also forwards a Unix socket back to the laptop, at `~/.nearhost/<id>.sock` on the server, so that a coding agent there reaches Nearhost. It is added after the master connects and again after each reconnect, and a server that refuses it only loses that: its projects serve as usual. See [How agents reach Nearhost](/pr-preview/pr-96/docs/coding-agents/how-it-works/). ## Reconnection and backoff If the master exits, Nearhost starts it again, waiting 1 second, then twice as long each time, up to 30 seconds. A master that does not connect within 20 seconds is stopped and tried again. While it waits, the server shows `reconnecting · attempt 3 · next in 8s`, and its projects show `degraded`. Some errors do not go away by retrying: `Permission denied`, a host key that failed or changed, and too many authentication failures. After three of those in a row, Nearhost stops and the server shows `auth failed`, with the fix: run `ssh <host>` once in a terminal, then press `r`. ## Reconnecting and dropping On a server’s row in the interface: * `r` reconnects now, without waiting for the next attempt. On Home, `r` does this for every server that cannot connect. * `c` drops the connection and holds it closed. Its projects keep their sites and show `degraded`, and starting one there is refused until you press `c` again to connect. ## Shutting down On exit, Nearhost stops every master with `-O exit`, and stops it outright if it has not gone after 3 seconds. A socket left by a crash is checked before each start, and cleared. ## What is stored Nothing beyond the host string. No keys, passwords or sockets are kept in `config.yaml`.

# The hosts file

> How Nearhost keeps one delimited block in /etc/hosts to resolve project names.

`.test` is a reserved top-level domain that is never public, so Nearhost resolves aliases through `/etc/hosts` and not through DNS. ## The owned block Nearhost owns one block and touches nothing else in the file: 
```text
# nearhost:start
127.0.0.1 myapp.test
::1 myapp.test
127.0.0.1 other.test
::1 other.test
# nearhost:end
```
 Each name has a `127.0.0.1` line and a `::1` line, so a browser that tries IPv6 first still reaches Nearhost. Nearhost 0.7 and earlier wrote only the `127.0.0.1` line. The block always lists `.test` names, running or not, sorted. Any other [main name](/pr-preview/pr-96/docs/reference/config/#main-name) is listed only while its project is enabled, and only if DNS does not already resolve it to loopback addresses alone. Each enabled project’s exact web hosts are listed too, under the same DNS rule for names that do not end in `.test`. `localhost` is never listed, because your system already maps it to loopback and Nearhost leaves that mapping alone. If the machine’s nameserver runs on this machine, as systemd-resolved’s does on Linux, Nearhost cannot tell what DNS would say, because that nameserver reads the hosts file too. It keeps the name in the block, so the entry stays where it is. Nearhost 0.7 and earlier dropped it. Wildcard patterns are never listed either, because a hosts file cannot express them: a pattern’s names need DNS that sends them to 127.0.0.1, and `nearhost doctor` reports any that do not resolve. With no projects, the block is removed rather than left empty. ## How changes are applied Each time a project starts, Nearhost works out the block the file should have. If the file already has it, nothing happens. If not, Nearhost runs itself as root to rewrite the block: 
```sh
sudo nearhost hosts apply --file /etc/hosts
```
 with the aliases on its standard input, one per line. The command is an internal step, so it does not appear in `nearhost --help`. Only one project’s start asks at a time. In the interface, the password is asked for in a box, and `sudo` remembers it for a few minutes. Where `sudo` asks every time, Nearhost hands over to the terminal for it. See [First run](/pr-preview/pr-96/docs/getting-started/first-run/#the-password-box). `nearhost up` asks in the terminal. From Nearhost 0.8.0, Nearhost runs `sudo` from `/usr/bin`, `/bin`, `/usr/local/bin` or `/run/wrappers/bin`, and only a copy owned by root, never one found on your `PATH`. The rewrite changes only the content between the markers, and adds the block at the end of the file if it is absent. It writes a new file and renames it into place, keeping the file’s permissions, and on Linux its SELinux label and access lists. If you cancel the password, the project stays stopped, and Home’s `hosts` row shows which aliases are missing. Start the project again to retry. ## Managing it yourself Run Nearhost with `--no-hosts` to leave `/etc/hosts` alone, for example when you add the aliases yourself. `nearhost doctor` reports whether the block has every alias. A block written by Nearhost 0.7 or earlier has only the `127.0.0.1` lines. Doctor warns about that, as the block “has no IPv6 (::1) entries”, and does not fail. `nearhost up` rewrites it with the `::1` lines. ## Removing it Nothing is removed when Nearhost quits. To remove the block, which asks for your password through `sudo`: 
```sh
nearhost hosts clean
```

# The request log

> How Nearhost keeps each request and response in memory, and how to look at them and send them again.

Every request the proxy passes on is logged against its project, with its method, path, status and time. Nearhost also keeps the request and its response, bodies included, in memory, so you can look inside them and send them again. ## Opening it Press `l` for the full-screen log of the selected row: a project, a server, or from Home, everything. `tab` moves between all entries, requests, events and errors, and `/` searches. Choose a request with `j` and `k`, then: | Key | Action | | ------- | ------------------------------------------------------- | | `enter` | Open it: its headers and bodies, and the route it took. | | `v` | Show or hide cookies and authorisation headers. | | `c` | Copy it as a `curl` command. | | `r` | Send it again. | | `G` | Jump to the end and follow new lines. | | `w` | Wrap long lines. | | `esc` | Clear the search, or close the log. | Compressed bodies are unpacked, and JSON is laid out to read. ## Sending a request again `r` sends the request through the proxy again, so it is logged like any other, and shows the status that came back. `GET`, `HEAD` and `OPTIONS` are sent at once. Anything else could change something, so Nearhost asks first, and `y` sends it. A request cannot be sent again when it was a WebSocket or another upgraded connection, when only part of its body was kept, or when it is no longer kept. ## What is kept * Each body up to 64 KiB. * The latest 1000 requests, and at most 32 MiB of bodies. The oldest go first. * Real header values, including cookies, which the log itself hides. It all lives in memory and is gone when Nearhost quits. To keep nothing, run Nearhost with `--no-capture`. Requests are still logged, but their bodies are not kept and they cannot be sent again.

# TLS and the proxy

> How the embedded Caddy proxy and the local certificate authority serve each alias over HTTPS.

Caddy runs inside the Nearhost process, with its storage in Nearhost’s data folder, under `nearhost/caddy`: `~/Library/Application Support/nearhost/caddy` on macOS and `~/.local/share/nearhost/caddy` on Linux, or `$XDG_DATA_HOME/nearhost/caddy` on either when that variable is set to an absolute path. It listens on 443 for HTTPS, on 80 only to redirect to HTTPS, with a 308, and on 6327 for Nearhost’s page. To use other ports, run Nearhost with `--https-port`, `--http-port` and `--web-port`. It answers only this machine, and, for a project whose `.nearhostrc` sets `docker_clients`, containers on this machine’s Docker networks. A request from another computer, or for a name Nearhost does not serve, has its connection closed with no answer. While Nearhost runs, even with no projects, `https://localhost:6327` shows Nearhost’s own page. No project uses that port, so the page is there whatever the projects serve. `https://localhost` shows the same page too, unless a project serves `localhost` itself. `--web-port` moves the port, and `--web-port 0` turns it off, leaving only `https://localhost`. If the page’s port is taken, Nearhost starts without the page and says so, and `nearhost doctor` warns. Pass `--web-port` to choose another port. A taken HTTPS or HTTP port is different: Nearhost does not start the proxy. The page needs Nearhost 0.8.0 or later. ## The local CA The internal certificate authority, “Nearhost Local CA”, is created the first time Nearhost starts. Nearhost never ships a shared key or a wildcard certificate, and Caddy never installs the authority by itself. Trusting it puts its root into the system trust store, which asks for your password once: the System keychain on macOS, your distribution’s certificate store on Linux. It also updates the separate stores that Firefox and Linux Chromium-based browsers use, when `certutil` is installed. If the system already trusts it, only the browser stores are updated, with no password. ### Where its key is kept The CA’s private key is in the `caddy` folder named above, under `pki/authorities/local`. Anyone who has it can sign certificates that your browser trusts, so keep that folder out of dotfiles repositories and shared backups. Your config, `~/.config/nearhost/config.yaml` (or under `$XDG_CONFIG_HOME` when that is set), holds no keys and is safe to share. From Nearhost 0.8.0 the key is in the data folder. Earlier versions kept it in `~/.config/nearhost/caddy`, or `$XDG_CONFIG_HOME/nearhost/caddy` when that variable is set. The next time you run `nearhost`, `nearhost up`, `nearhost trust` or `nearhost untrust`, Nearhost moves an existing old folder there, so the CA you already trust stays the same. It does not move it while another Nearhost is running. If a copy of the old folder is left behind, `nearhost doctor` warns with `old CA copy` and says which folder to delete. Trust it from the welcome box the first time you start Nearhost, or at any time with `nearhost trust`. `nearhost untrust` removes the CA from the system and browser stores. It leaves the key’s folder where it is. See [First run](/pr-preview/pr-96/docs/getting-started/first-run/) and, for Linux and Firefox, [Install](/pr-preview/pr-96/docs/getting-started/install/). Home shows whether it is trusted and when it expires. The date turns amber in the last 30 days. ## Per-name certificates Leaf certificates are issued automatically. Each exact name a project serves gets its own. A name under a wildcard pattern gets one the first time it is visited. Because the CA is created on your machine, nobody else holds a key that can sign for your `.test` names. ## What the proxy sets Each web route of a running project is served at its hosts, and the first one also at `https://<alias>`. Requests go to the route’s local forward, or for a local project to its port. * The `Host` header is passed through unchanged. * `X-Forwarded-Proto: https` and `X-Forwarded-For` are set. * `Via` names Nearhost and its version, as `1.1 Nearhost (0.8.0)`, on the request and the response. Entries from other proxies are kept. From Nearhost 0.8.0; earlier versions said `Caddy`. * WebSocket upgrades pass through. * Responses are not buffered. ## Reloads without dropping connections Config changes apply through Caddy’s in-process reload. Starting or stopping a project leaves the connections of other projects open, and open WebSockets, such as hot reload, stay connected. The proxy also keeps the requests it passes on, so you can look at them and send them again. See [The request log](/pr-preview/pr-96/docs/concepts/the-request-log/). If the browser still warns about the certificate, see [The CA is not trusted](/pr-preview/pr-96/docs/troubleshooting/troubleshooting/#the-ca-is-not-trusted). For why local dev wants a real HTTPS name, see [HTTPS on a local dev domain](/pr-preview/pr-96/docs/guides/https-on-a-local-dev-domain/).

# What Nearhost changes on your machine

> Every file, privilege, port and network request Nearhost uses on your laptop and your servers, and how to undo each one.

Nearhost asks for your password, trusts a certificate authority and edits `/etc/hosts`, so you should know exactly what it does. This page lists all of it, on your laptop and on your servers, and how to undo each part. The other concept pages explain the reasons; this one is the inventory. ## Files on your laptop | Path | What it holds | | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | | `~/.config/nearhost/` | `config.yaml` with your servers and projects, a lock file, an install id, presets you enabled, cached registry indexes, and `run/` with SSH sockets | | `~/Library/Application Support/nearhost/caddy` (macOS) `~/.local/share/nearhost/caddy` (Linux) | The local certificate authority, its private key and the certificates it signed, readable only by you | | `~/.cache/nearhost/update.json` | When Nearhost last checked for a new release | | `~/.nearhost/` | The socket coding agents on this machine use, readable only by you | An absolute `XDG_CONFIG_HOME`, `XDG_DATA_HOME` or `XDG_CACHE_HOME` moves the first three. The install id is six random characters plus a hash of the machine id. It never leaves your machine. Nearhost writes no log files. Its log is shown in the interface, or printed by `nearhost up`. Nearhost writes nothing to your projects unless you run `nearhost export`, which writes a `.nearhostrc`. A coding agent edits files itself, not through Nearhost. ## What runs as root Nearhost never runs as root itself. It uses `sudo` for two things, and from Nearhost 0.8.0 only the `sudo` in a system directory, such as `/usr/bin`, never one found on your `PATH`. * **The hosts file.** When a project starts and the [block Nearhost owns](/pr-preview/pr-96/docs/concepts/the-hosts-file/) in `/etc/hosts` is not what it should be, Nearhost runs its own binary as root, `sudo nearhost hosts apply --file /etc/hosts`, which rewrites that block and nothing else. If `sudo` still holds your password from the last few minutes, this happens without asking again. `--no-hosts` turns it off. * **Trusting the certificate authority.** Only when you run `nearhost trust` or accept the welcome box. On macOS it adds the root certificate to the System keychain with `security add-trusted-cert`. On Linux it copies the certificate into your distribution’s anchors folder and runs `update-ca-certificates`, `update-ca-trust` or `trust extract-compat`. When `certutil` is installed, it also updates the stores that Firefox and, on Linux, Chromium-based browsers keep for themselves, as you, with no password. On Linux, binding ports 80 and 443 needs `cap_net_bind_service`. Nearhost itself never sets it. The install script offers to run `sudo setcap` when you run a downloaded copy from a terminal, and asks first. Through `curl | sh`, or `nearhost update`, it only prints the command, as `nearhost doctor` does. ## The certificate authority Nearhost creates its certificate authority on your machine the first time it starts: an ECDSA P-256 root, valid for ten years, with an intermediate that renews every week. Certificates for your names last 12 hours and renew automatically. Nearhost issues them only for names you serve. Nothing limits the root to `.test`, the same as mkcert’s root. Anyone with its private key could make certificates your browser trusts for any domain. The key never leaves the `caddy` folder above, and that folder is readable only by you, but keep it out of dotfiles repositories and shared backups. See [TLS and the proxy](/pr-preview/pr-96/docs/concepts/tls-and-the-proxy/). ## Ports on your laptop While Nearhost runs, it listens on: * **443** for HTTPS, over TCP and, for HTTP/3, UDP * **80**, only to redirect to HTTPS * **6327** for [Nearhost’s page](/pr-preview/pr-96/docs/concepts/tls-and-the-proxy/) * one port on `127.0.0.1` per forwarded route, and for a `loopback` route the same port on `::1` too, when the machine has IPv6 loopback The first three listen on every interface, because macOS lets a program that is not root bind a low port only that way. They answer only this machine: another computer’s connection is closed before it gets a certificate or a response. A project with `docker_clients` in its [`.nearhostrc`](/pr-preview/pr-96/docs/reference/nearhostrc/) is also answered for your Docker networks. Until Docker first reports them, Nearhost uses Docker’s default range, `172.16.0.0/12`, which some home and office networks share. `--https-port`, `--http-port` and `--web-port` move the ports, and `--web-port 0` turns the page off. When Nearhost quits, all of them close. ## Network requests Nearhost makes these requests and no others. It has no telemetry, no analytics and no account. * **SSH to your servers**, through your own `ssh` and `~/.ssh/config`. * **The update check.** At most once a day, `GET https://api.github.com/repos/nearhost/nearhost/releases/latest`. Set `NEARHOST_NO_UPDATE_CHECK=1` to turn it off. * **Preset registries.** Only registries you have chosen to trust, from `raw.githubusercontent.com`, when you add a project or manage presets. Each preset is checked against the hash in the registry’s index. With no trusted registry, Nearhost requests nothing. See [Presets and registries](/pr-preview/pr-96/docs/concepts/presets-and-registries/). * **DNS.** To decide which names need a hosts entry, Nearhost asks your configured nameserver for names that do not end in `.test`. * **Docker**, through its local socket, for projects with `docker_clients`. * **`nearhost update`**, only when you run it. It asks GitHub for the latest release, then runs your package manager or the install script, which download it. ## Requests through the proxy To show request bodies and send requests again, Nearhost keeps recent requests and responses in memory while it runs: the last thousand or so, bodies up to 64 KiB, 32 MiB in all. They are never written to disk and are gone when Nearhost quits. The log hides `Cookie` and `Authorization` headers. `--no-capture` turns capture off. See [The request log](/pr-preview/pr-96/docs/concepts/the-request-log/). ## On your servers Nearhost installs nothing on a server and opens no ports there. It runs your `ssh`, and through that connection it: * runs `true` once to check that the connection works * forwards each route’s port to your laptop * reads files over SFTP: `.env`, `.env.local`, `.nearhostrc`, Compose files and any files an enabled preset names * creates `~/.nearhost`, readable only by you, with a socket for coding agents on the server When Nearhost quits, the forwards and the connection close. `~/.nearhost` stays, and may hold a stale socket that the next connection replaces. A `.nearhostrc` written by `nearhost export` stays in the project. See [SSH transport](/pr-preview/pr-96/docs/concepts/ssh-transport/). ## What coding agents can do A coding agent reaches Nearhost through a socket that only your user can open, and sees only the projects of the machine it runs on. Without asking you, it can list those projects, run `nearhost doctor` on a folder, and ask Nearhost to reload a project’s `.nearhostrc`. Nearhost applies changes such as ports and new `.test` hosts straight away and saves them to `config.yaml`; the agent never edits that file itself. Anything else, including other domains, wildcards, `localhost` and `docker_clients`, waits for you to approve it. See [How agents reach Nearhost](/pr-preview/pr-96/docs/coding-agents/how-it-works/). ## Undo everything 1. Run `nearhost untrust` to stop your system and browsers trusting the certificate authority. 2. Run `nearhost hosts clean` to remove the block from `/etc/hosts`. 3. On Linux, the port capability goes with the binary when you uninstall it. To drop it and keep Nearhost, run `sudo setcap -r` on the binary `nearhost doctor` names. 4. Uninstall Nearhost the way you installed it, such as `brew uninstall nearhost` or `npm uninstall -g @nearhost/cli`. 5. Delete `~/.config/nearhost`, the data folder that holds `caddy`, `~/.cache/nearhost` and `~/.nearhost`. 6. On each server, delete `~/.nearhost`, and any `.nearhostrc` you no longer want. Run steps 1 and 2 before step 4, while the `nearhost` command still exists. ## Reporting a problem If you find a way around any of this, report it privately, as the [security policy](https://github.com/nearhost/nearhost/security/policy) explains. Please don’t open a public issue.

# Advisories

> The advice Nearhost gives about a project, when each appears and how to fix it.

Advisories are shown, never applied. Nearhost does not edit your project’s files. In the interface they appear in amber boxes under a project’s routes, and `y` copies their snippets. `nearhost add` prints each one as `Advisory (<id>): <message>`. One advisory is built in. The others come from the official presets and appear only when that preset is enabled and applies to the project. Any preset can add its own, and a later preset can replace or remove an earlier one’s by its id. See [Presets and registries](/pr-preview/pr-96/docs/concepts/presets-and-registries/). ## Loopback port clash `loopback-clash`, built in. Appears when another enabled project forwards the same loopback port: 
```text
Port 5173 is also forwarded to this machine by project "shop". Only one can bind it. Give this project its own port.
```
 When the port comes from a variable, the snippet sets it to a free port: 
```sh
VITE_PORT=5174
```
 `nearhost add` refuses to save a project with a clash unless you add it with `--disabled`, and a config file with one does not load. ## Vite on the default port `vite-default-port`, from `nearhost/vite`. Appears when the Vite config sets no `server.port`, unless it reads `VITE_PORT` and `.env` sets it. Any `server.port` counts, a number, an expression such as `Number(process.env.APP_VITE_PORT) || 5291` or the shorthand `server: { port }`, but not one that is commented out. A port whose value reads `VITE_PORT` counts only while `.env` sets `VITE_PORT`. Vite will use 5173, which other Vite projects also use, so set a port in the Vite config. The snippet suggests a free one: vite.config.ts 
```ts
export default defineConfig({
  server: {
    port: 5174,
  },
});
```
 Under Laravel Sail, `nearhost/sail` replaces it with the same advice for `.env`. `laravel-vite-plugin` reads `VITE_PORT` from `.env` or the environment, so the advice does not appear when the Compose file’s `environment` sets `VITE_PORT` to a port other than 5173. A default under `ports`, such as `${VITE_PORT:-5176}`, does not count: it only maps the port, and Vite in the container still listens on 5173. Its snippet: 
```sh
VITE_PORT=5174
```
 ## allowedHosts missing `allowed-hosts`, from `nearhost/vite`. Appears when `server.allowedHosts` does not include the alias, unless Vite serves HTTPS itself or allows every host. Vite rejects requests for hostnames it does not know. vite.config.ts 
```ts
export default defineConfig({
  server: {
    allowedHosts: ['myapp.test'],
  },
});
```
 `nearhost/sail` turns it off, since under Sail the browser reaches Vite at `localhost`, not at the alias. ## APP_URL mismatch `app-url`, from `nearhost/laravel`. Appears when `APP_URL` in `.env` is missing, is not `https://`, has a port, or names a host the project does not serve. Generated links use that value, so set it to one of the project’s addresses, with `https` and no port. The suggested line keeps the host when the project serves it, and uses the alias otherwise: 
```sh
APP_URL=https://myapp.test
```
 See [Discovery](/pr-preview/pr-96/docs/concepts/discovery/) for how advisories are produced.

# config.yaml

> Every key in the Nearhost configuration file.

The file is `~/.config/nearhost/config.yaml`, or `$XDG_CONFIG_HOME/nearhost/config.yaml` when that variable is an absolute path. `--config <file>` points any command at another file. Nearhost writes the file whenever you add or change something in the interface, or run `nearhost add`, `nearhost preset` or `nearhost preset registry`. `nearhost up` writes it too, when a project’s `.nearhostrc` has changed in a way that needs no approval. It reads the file again first, so hand edits are kept, but comments and formatting are not. 
```yaml
servers:
  - name: mini # free text; "local" is reserved and implicit
    ssh_host: mini # alias from ~/.ssh/config, or user@host
projects:
  - name: myapp
    server: mini
    path: /home/dev/code/myapp
    alias: myapp.test # the main name: <name>.test, or any domain
    enabled: true # start automatically when Nearhost launches
    routes:
      - port: 8080 # port on the server
        role: web # web | loopback | ignore
        label: 'app (APP_PORT)'
      - port: 5173
        role: loopback
        label: 'Vite (vite.config)'
      - port: 5432
        role: ignore
        label: 'db'
registries:
  - alias: nearhost
    repo: nearhost/presets
presets:
  - name: nearhost/vite
    ref: e6c0be9e14dc89ec5c19bb1bc7d155c1029c298d
    sha256: 024643158cc1d55819e3f62d9d3e429cc8b15dae396cf036db9d573815c9d80e
```
 ## Keys | Key | Type | Meaning | | --------------------------- | ------- | --------------------------------------------------------------------------------------------------------------- | | `servers[].name` | string | Free text. `local` is reserved. | | `servers[].ssh_host` | string | An alias from `~/.ssh/config`, or `user@host`. For another port, use an alias with `Port`. | | `projects[].name` | string | The project name. | | `projects[].server` | string | The `name` of a server, or `local`. | | `projects[].path` | string | The project directory on that server. | | `projects[].alias` | string | The project’s main name, served over HTTPS. `<name>.test` unless you change it. See below. | | `projects[].enabled` | boolean | Start the project automatically when Nearhost launches. | | `projects[].routes[].port` | integer | The port on the server. | | `projects[].routes[].role` | string | One of `web`, `loopback` or `ignore`. | | `projects[].routes[].label` | string | Optional. A description, usually from discovery. | | `projects[].routes[].hosts` | list | Optional, web routes only. More names to serve the route at: exact names or wildcard patterns. | | `projects[].nearhostrc` | map | Written by Nearhost: the project’s `.nearhostrc` as Nearhost last applied it. Do not edit it. | | `registries[].alias` | string | The name a registry’s presets are known by, as in `nearhost/vite`. | | `registries[].repo` | string | The registry’s GitHub repository, as `owner/name`. | | `registry_prompt` | boolean | `false` stops Nearhost offering to trust the official registry. Absent means ask. | | `notifications` | boolean | `false` stops the terminal notification when an agent asks for a project, preview or document. Absent means on. | | `presets[].name` | string | An enabled preset: `<registry>/<name>`, or a plain name for a local file. | | `presets[].ref` | string | For a registry preset, the commit it was installed from. | | `presets[].sha256` | string | For a registry preset, the hash of its file. | Use `nearhost preset` and `nearhost preset registry` rather than editing the last five by hand. See [Presets and registries](/pr-preview/pr-96/docs/concepts/presets-and-registries/). ## Main name `projects[].alias` is the project’s main name: the address Nearhost shows, prints after `nearhost add` and gives to agents. It is `<name>.test` by default. It can be any one exact domain instead, such as `app.local.example.com`. A main name must be lowercase. It cannot be a wildcard pattern, `localhost` or an IP address. A main name that does not end in `.test` is a real domain, so it needs your approval before it goes live. Typing it with `nearhost add --alias` approves it. A name from a `.nearhostrc` that you did not type is asked about in the terminal by `nearhost add`. When a `.nearhostrc` or an agent proposes one later, it waits for you in the interface, and the old name keeps serving until you approve. The hosts file treats the two kinds differently: * A `.test` name is written to `/etc/hosts` for every project, enabled or not. * Any other name is written only while its project is enabled, and unless DNS already resolves it only to this machine’s loopback address. A disabled project does not hide the real site. A project has one main name. If you switch to a real domain, the `<name>.test` address stops working. A project’s `.nearhostrc` can set the main name with `alias:`, filled from the project’s `.env` so each worktree can have its own. `nearhost add --alias` wins over the file, and the file wins over `<name>.test`. See [`.nearhostrc`](/pr-preview/pr-96/docs/reference/nearhostrc/#keys). ## Validation * Server names are unique, each server has a host, and `local` is not used as a name. A host may not start with `-`, which `ssh` would read as an option. * Project names are unique, and each project’s server exists. * Aliases are unique across projects, ignoring case. An alias that is not a valid main name does not start, and `nearhost doctor` reports it. * Each project has at least one `web` route. The first is served at the main name. Every other web route needs at least one host. Ports are from 1 to 65535. * Only web routes have hosts, and a project serves each host once. * `docker_clients` in a `.nearhostrc` works only for projects on `local`. * Loopback ports are unique across enabled projects. * Registry aliases are lowercase letters, digits and single hyphens. Each preset’s registry is trusted. Registry presets have `ref` and `sha256`, and local ones do not. If the file is not valid YAML, Nearhost exits with the error and its line. If it breaks a rule above, Nearhost exits naming the file and the problem. `nearhost doctor` reports either without exiting. ## Beside the config The folder that holds `config.yaml` also holds: * `presets/`: installed presets * `registry/`: each trusted registry’s cached index * `run/`: the SSH control sockets * `config.yaml.lock`: held while a command or the interface changes the config, so two never save over each other. Leave it in place. From Nearhost 0.8.0. The proxy’s storage, including the local certificate authority, is not in this folder. It is the `caddy` folder in Nearhost’s data directory: `~/Library/Application Support/nearhost/caddy` on macOS and `~/.local/share/nearhost/caddy` on Linux, or `$XDG_DATA_HOME/nearhost/caddy` on either when that variable is set to an absolute path. Nearhost 0.7 and earlier kept it beside the config. See [The local CA](/pr-preview/pr-96/docs/concepts/tls-and-the-proxy/#the-local-ca). ## The local server The `local` server always exists and needs no configuration. It does not appear under `servers`, and it may not be removed or renamed. A route on it is `web` or `ignore`, because a loopback forward would point the port at itself. See [Routes and roles](/pr-preview/pr-96/docs/concepts/routes-and-roles/).

# .nearhostrc

> Every key in a project's .nearhostrc, how its variables are filled, and what it asks you to approve.

A `.nearhostrc` is a YAML file in a project’s root directory. You commit it with the project, so everyone who adds the project gets the same ports, hosts and main name, and each worktree can fill them from its own `.env`. The file only ever proposes. A host or main name that is not `.test`, a wildcard, `localhost` and Docker access all wait for your approval before they go live. See [Approval](#approval). 
```yaml
version: 1
alias: ${APP_HOST:-app.local.example.com}
routes:
  - port: ${APP_PORT:-8000}
    label: app
    hosts:
      - api.local.example.com
      - '*.status.local.example.com'
  - port: ${FORWARD_REVERB_PORT:-8080}
    label: reverb
    hosts: [ws.local.example.com]
  - port: ${FORWARD_MINIO_PORT:-9000}
    label: minio
    hosts: [files.local.example.com]
  - port: ${VITE_PORT:-5173}
    role: ignore
    label: vite
docker_clients: true
```
 With this `.env` beside it, the app is served at `https://app.local.example.com` and `https://api.local.example.com` from port 8010. A name one label under `status.local.example.com`, such as `eu.status.local.example.com`, reaches the same port; the hosts file cannot hold a pattern, so its names need DNS that points them at this machine. Reverb is served at `ws.local.example.com` from port 8090, and MinIO at `files.local.example.com` from port 9010: 
```ini
APP_PORT=8010
FORWARD_REVERB_PORT=8090
FORWARD_MINIO_PORT=9010
```
 ## Keys | Key | Type | Meaning | | ---------------- | ------- | -------------------------------------------------------------------------------------------------------------------------- | | `version` | integer | Required. Must be `1`. | | `alias` | string | Optional. The project’s [main name](/pr-preview/pr-96/docs/reference/config/#main-name): `<name>.test`, or any one domain. | | `routes[].port` | integer | Required. The port on the server. A number from 1 to 65535, or a variable that gives one. | | `routes[].role` | string | Optional. `web`, `loopback` or `ignore`. `web` when left out. | | `routes[].label` | string | Optional. A description, shown with the route. | | `routes[].hosts` | list | Optional, web routes only. Names to serve the route at: exact names or wildcard patterns. | | `docker_clients` | boolean | Optional. `true` serves the project to Docker containers on this machine too. See [Docker clients](#docker-clients). | The roles mean what they mean in `config.yaml`. See [Routes and roles](/pr-preview/pr-96/docs/concepts/routes-and-roles/). The file is the authority on the routes it lists. Their hosts replace any that presets found for those ports. A port the project has that the file does not list stays visible, but a web one becomes `ignore`, so only the file says what is served. `nearhost add --alias` wins over `alias:`, and `alias:` wins over `<name>.test`. Removing `alias:` from the file leaves the current main name as it is. ## Rules * A file that lists routes needs at least one `web` route among them. * The first web route is served at the project’s main name. Every later web route needs at least one host. * A port, or a host, listed twice is an error. * Only web routes have hosts. * The main name may be listed as a host only on the first web route, where it is served anyway. * `docker_clients` works only for a project on this machine, not one on a server. * Hosts and the main name must be lowercase. The main name cannot be a wildcard pattern, `localhost` or an IP address. ## Variables `${VAR}` and `${VAR:-default}` work in ports, hosts, labels, roles and the alias. They are filled from `.env.local`, then `.env`, in the project’s directory, so a value in `.env.local` wins. They are never filled from Nearhost’s own environment. A variable with no value and no default is an error that names it: 
```text
.nearhostrc: ${APP_PORT} has no value in .env.local or .env, and no default
```
 A variable can fill part of a value, as in `app.${APP_DOMAIN}`. Worktrees of one repository can then share the committed file and each serve its own hosts. Approval works on the filled values, so you approve the names that will actually be served, and a change in `.env` that gives a new real domain asks again. ## Errors Every error in the file itself starts with `.nearhostrc`. `nearhost add` stops with it, and the interface and `nearhost doctor` show it with the project. A key this version of Nearhost does not know is an error, rather than being ignored: 
```text
.nearhostrc: line 4: key "hostz" is not understood by this version of Nearhost; update Nearhost, or remove it
```
 So is a `version` newer than this Nearhost understands: 
```text
.nearhostrc is version 2; this Nearhost understands version 1, so update Nearhost
```
 Run `nearhost update` for the second. For the first, check the key’s spelling against [Keys](#keys). ## Approval These need your approval before they go live: * a host that does not end in `.test`; * a wildcard pattern, even one under `.test`; * `localhost`; * a main name that does not end in `.test`; * `docker_clients: true`. A `.test` host, a port, a label or a role needs none. Neither does a host the project already serves. Each front end asks in its own way: * **The interface.** When you add a project, the last step lists what needs approval, and `enter` approves it and saves. When a project’s file changes later, the project shows `.nearhostrc asks for 1 change that needs approval · a to review`. Press `a` to see what it asks for, then `y` to approve, `n` to decline or `esc` to leave it for later. A declined change is not asked about again until the file changes or Nearhost restarts. * **`nearhost add`.** At a terminal it lists each item and asks `Approve these? [y/N]`. A host typed with `--host`, or a main name typed with `--alias`, is approved by typing it. Without a terminal it adds nothing, and names the items. For the file at the top of this page: 
  ```text
  nearhost: not added: this project asks for things that need your approval (*.status.local.example.com, api.local.example.com, ws.local.example.com, files.local.example.com, app.local.example.com, docker_clients); run nearhost add in a terminal, or open nearhost
  ```
 * **`nearhost up`.** It cannot approve anything. A project whose file asks for something new keeps serving what was approved before, and its log says what is waiting. Open `nearhost` to approve it. Nothing approves itself. ## When it is read Nearhost reads the file, and applies what it finds: * when a project starts; * when you press `r` on a project in the interface; * when an agent asks Nearhost to read it again, or runs the doctor on the project. A change that needs no approval, such as a port moved in `.env`, a new label or a new `.test` host, applies at once and is saved to `config.yaml`. A change that needs approval waits, and the routes approved before keep serving until you approve it. If the file has an error, or is deleted after it was approved, the project keeps serving what was approved and shows the problem. `nearhost doctor` on the command line reads the file too, but only reports. It applies and saves nothing. It reports a file with an error, a change that waits for approval, and a change that needs none but has not been applied yet. ## Docker clients Nearhost answers only this machine. On Linux, a request from a container comes from a Docker network, not from this machine’s loopback address, so Nearhost drops it. `docker_clients: true` also serves the project to the networks Docker has on this machine, while other projects stay loopback-only. It works only for a project on this machine, and it always needs your approval. Docker Desktop on macOS already delivers container requests from 127.0.0.1, so this matters on Linux. A container also needs to find the host and trust the local certificate authority. See [Callbacks from Docker containers to a local HTTPS domain](/pr-preview/pr-96/docs/guides/container-callbacks/). ## A file without routes To set only the main name, and leave the routes to discovery and to you, give the file `version` and `alias`: 
```yaml
version: 1
alias: ${APP_HOST:-app.local.example.com}
```
 The routes stay as discovery found them or as you set them. The file removes only the hosts that an earlier, approved version of it gave, and the main name from any route other than the first web route. A later web route left with no hosts once the main name is removed becomes `ignore`.

# Troubleshooting

> Symptoms Nearhost reports and the fix for each.

Every failure attaches to the thing that failed, with why it happened and how to fix it. A failure in one project or server never affects another. Home lists what needs you under problems. `nearhost doctor` checks most of the causes below at once. ## Port 443 or 80 already in use The proxy does not start. Home shows `proxy down`, names the port and, where it can, the program holding it. Quit that program, or run Nearhost with `--https-port` and `--http-port`. Another local proxy is the usual cause: nginx, Caddy, Herd or Valet. On Linux, also check that the binary may bind low ports. See [Install](/pr-preview/pr-96/docs/getting-started/install/). If Home says the port needs permission to bind, nothing holds it, but this user may not use it. On Linux, the fix under it is the `setcap` command for the binary, as in [Allow binding ports 80 and 443](/pr-preview/pr-96/docs/getting-started/install/#allow-binding-ports-80-and-443); run it, then start Nearhost again. For an npm install, use the command `nearhost doctor` prints, which names the real binary. From Nearhost 0.8.0. ## Port 6327 already in use Nearhost starts, serves every project and leaves out Nearhost’s page, and the log says `port 6327 is in use; serving without Nearhost's page`. `nearhost doctor` warns about it. Another Nearhost already running is the usual cause. Otherwise pass `--web-port` with a free port, or `--web-port 0` to turn off the page’s own port, leaving it at `https://localhost`. From Nearhost 0.8.0. ## A loopback port is already bound The project goes into `error`, naming the port and the program holding it on this machine. Its other routes still start. Stop that program, or move the project’s dev server to another port and edit the route. For Vite that is `server.port` in the Vite config, or `VITE_PORT` under Laravel Sail. Then press `enter` on the project to start it again. From Nearhost 0.7.0, on a laptop with the IPv6 loopback, a loopback forward answers on `[::1]` as well as `127.0.0.1`, so a program listening on either address holds the port. The usual one is a Vite dev server running on your laptop, which often listens on `::1` alone. To see every program on the port the error names, on both addresses, run this with that port in place of `<port>`: 
```sh
lsof -nP -iTCP:<port> -sTCP:LISTEN
```
 On older versions, such a program could answer the browser in the forward’s place, so the page loaded your laptop’s scripts instead of the server’s. Run `nearhost update` to get the check. ## The password was cancelled When the hosts block needs a project’s alias, Nearhost asks for your password in a box. If you cancel it, or get it wrong three times, the project stays `stopped`, its alias is not added to `/etc/hosts`, and Home’s `hosts` row shows it as missing. Press `enter` on the project to try again. Or add the alias to `/etc/hosts` yourself and run Nearhost with `--no-hosts`. See [The hosts file](/pr-preview/pr-96/docs/concepts/the-hosts-file/). ## Too many password prompts `sudo` remembers your password for a few minutes, so Nearhost usually asks once for several changes. If it asks in the terminal instead of the box, `sudo` is set to ask every time. On a Mac you can use Touch ID instead of typing it. See [First run](/pr-preview/pr-96/docs/getting-started/first-run/#touch-id-on-a-mac). ## No root-owned sudo `nearhost trust`, `nearhost untrust` and changes to `/etc/hosts` stop with `no root-owned sudo in /usr/bin, /bin, /usr/local/bin or /run/wrappers/bin`. From Nearhost 0.8.0, Nearhost runs only a `sudo` in one of those folders that root owns, so a `sudo` elsewhere on your `PATH` is never handed your password. Install sudo there, or run the command as root. ## The CA is not trusted The proxy still runs, but browsers warn about the certificate. Home shows `local CA ● not trusted. Run nearhost trust`. Run: 
```sh
nearhost trust
```
 Firefox, and Chromium-based browsers on Linux, need `certutil` too. See [Install](/pr-preview/pr-96/docs/getting-started/install/). The CA’s expiry date turns amber 30 days before it runs out. ## Doctor warns about an old CA copy or a hosts block without IPv6 Both come from an upgrade, and both are warnings, not failures. `old CA copy` means `~/.config/nearhost/caddy` (or `$XDG_CONFIG_HOME/nearhost/caddy`), where Nearhost 0.7 and earlier kept the local CA, is still there beside the new folder in Nearhost’s data folder. It holds a copy of the CA’s private key. Check that `nearhost doctor` shows the CA as trusted, then delete the old folder. See [The local CA](/pr-preview/pr-96/docs/concepts/tls-and-the-proxy/#the-local-ca). `hosts block` saying the block has no IPv6 (`::1`) entries means an older Nearhost wrote it. Run `nearhost up`, which rewrites the block with the `::1` lines and asks for your password. ## SSH keeps reconnecting The server shows `reconnecting · attempt N · next in Ns`, and its projects show `degraded`. Caddy returns 502 meanwhile. Nearhost keeps trying by itself. If it keeps failing, read the error on the server, then run `ssh <host>` in a terminal. When that connects, press `r` to reconnect now. ## Authentication failed After three errors in a row that retrying cannot fix, such as `Permission denied` or a changed host key, Nearhost stops trying. The server shows `auth failed`, with the fix: 
```sh
ssh <host>
```
 Run it in a terminal and handle the host key, passphrase or `ssh-add` prompt. Then press `r`. On Home, `y` copies the command. ## Agents unavailable on a server The server’s sshd refuses the socket coding agents reach Nearhost on, usually because `sshd_config` sets `AllowStreamLocalForwarding no`. Set it to `yes`, reload sshd and press `r` on the server. `nearhost doctor` shows the same check. See [When agents cannot reach Nearhost](/pr-preview/pr-96/docs/coding-agents/troubleshooting/). ## A server shows dropped You pressed `c` on it, which holds its connection closed. Its projects wait. Press `c` again to connect it. ## Discovery found nothing The routes step says no ports were found and asks for the web port. Enter it, or from the command line use `nearhost add --web <port>`. If the project uses Compose, Vite or Laravel Sail, trust the official presets so discovery can read them. See [Discovery](/pr-preview/pr-96/docs/concepts/discovery/). ## Config file invalid Nearhost exits naming the file and the problem, with the line for a YAML error. Fix it in `~/.config/nearhost/config.yaml`. `nearhost doctor` reports the same without exiting. See [config.yaml](/pr-preview/pr-96/docs/reference/config/).

# Clerk sign-in on a remote dev server

> Run a Clerk and Next.js app at a local HTTPS domain, such as https://local.myapp.com, with hot reload working, when the dev server runs on another machine.

New to Nearhost? [Install it](/pr-preview/pr-96/docs/getting-started/install/) and [add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) first. This guide gets Clerk sign-in working at `https://local.myapp.com` while your Next.js app runs on another machine. The worked example uses Clerk’s Next.js SDK, `@clerk/nextjs`, with a Clerk development instance. The Clerk and Nearhost steps are the same for any stack. ## The symptom A Clerk development instance is relaxed about where your app runs. It is built for an app on `localhost`, and it does not ask you to register a domain or a callback URL. When the app runs on a server or a VM, though, `localhost` in your browser is not where the app is. A tunnel such as ngrok gets the page on screen, but often not much more. The page loads at the ngrok address, and then hot reload never connects. Recent versions of Next.js block requests for its dev resources, hot reload included, from any host it was not told about, and logs `Blocked cross-origin request to Next.js dev resource` on the server. Anything the app builds from a URL in its environment, such as an app URL set to `http://localhost:3000`, still points there. And the app is on the public internet while you work on it. Nearhost serves the remote app on your laptop at a name you choose, with a trusted certificate, over SSH. The browser sees one stable HTTPS origin, the page and its hot reload connection come from that origin, and nothing is public. If you only need one app and plain HTTP, forwarding port 3000 with `ssh -L` gets you `http://localhost:3000`, which a development instance accepts. Nearhost is for when you want HTTPS, a name per project, or a setup shaped like production. ## Pick a name Use a name under a domain you own, such as `local.myapp.com`. It needs no DNS record: Nearhost points it at your laptop through `/etc/hosts` while the project is enabled. When the project is disabled, the name resolves as it normally would. A real-domain name is shaped like production, where Clerk’s Frontend API lives on a subdomain of your domain. Clerk’s documentation does not say which local names a development instance accepts beyond `localhost`, so this guide uses a domain you own. If your production app already uses Clerk on `myapp.com`, use a name under a different domain you own, such as `local.myapp-dev.com`. Clerk’s docs say a separate setup will not work on the production domain, even on a separate subdomain. The examples below use `local.myapp.com`; swap in your name. ## Add the project On the command line, give the name with `--alias`: 
```sh
nearhost add --server mini '~/code/myapp' --alias local.myapp.com
```
 
```text
Added myapp on mini at https://local.myapp.com
Start it with `nearhost up`.
```
 A name that does not end in `.test` needs your approval, because it can hide the real site. Typing it with `--alias` counts as approval. To keep the name with the project, put it in a [`.nearhostrc`](/pr-preview/pr-96/docs/reference/nearhostrc/) in the project’s root: 
```yaml
version: 1
alias: local.myapp.com
```
 Run `nearhost add` without `--alias`, and it asks before using the name, since you did not type it: 
```text
$ nearhost add --server mini '~/code/myapp'
This project asks for these, which need your approval:
  local.myapp.com on port 3000 (a real domain)
Approve these? [y/N]
```
 The port is the one `next dev` listens on, 3000 unless you changed it. Give it the `web` role. The Next.js dev server serves pages, assets and hot reload from that one port, so it needs no `loopback` route. See [Add a project](/pr-preview/pr-96/docs/getting-started/add-a-project/) for the rest of the add flow, and [Main name](/pr-preview/pr-96/docs/reference/config/#main-name) for how the name is approved and written to the hosts file. ## Set up Clerk Use a development instance. It is the default for a new Clerk application, and its publishable key starts with `pk_test_`. A development instance has nothing to register for the new name. There is no redirect URI or allowed domain to add. Its Frontend API lives at a Clerk address ending in `accounts.dev`, and your app talks to it across sites whatever the app’s own name is. Clerk’s own docs use development keys on preview domains such as `*.vercel.app` in the same way. The **allowed origins** setting in Clerk’s API is for browser extensions and similar apps, not for a web app on a development instance. Leave it alone. In the Clerk Dashboard, open the **API keys** page and copy the keys into the app’s `.env.local`: 
```ini
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...
```
 These are the names `@clerk/nextjs` reads. If you set the app up with Clerk’s `init` command, they are already there. ## Set up the app Recent versions of Next.js only let their dev resources be requested from `localhost` and from the hostname `next dev` was started with. A page at `https://local.myapp.com` asks for them from `local.myapp.com`, so add that name to `allowedDevOrigins` in `next.config.ts`: 
```ts
import type { NextConfig } from 'next';


const nextConfig: NextConfig = {
  allowedDevOrigins: ['local.myapp.com'],
};


export default nextConfig;
```
 Write the hostname alone, without `https://` or a port. Restart `next dev` after changing it. The setting only affects development, so it is safe to commit. Clerk’s middleware stays as the quickstart has it: `clerkMiddleware()` in `proxy.ts` on Next.js 16 and later, or `middleware.ts` on Next.js 15 and earlier, at the root of the project or in `src/`. If you pass it `authorizedParties`, add the new origin, with the scheme: 
```ts
export default clerkMiddleware({
  authorizedParties: ['https://local.myapp.com'],
});
```
 Nearhost’s proxy passes the `Host` header through unchanged and sets `X-Forwarded-Proto: https`, so the app sees the name you browse to. If the app keeps its own public URL in an environment variable, such as `NEXT_PUBLIC_APP_URL`, set it to `https://local.myapp.com`. On another stack the idea is the same. Clerk needs nothing new, and the dev server needs to accept the new hostname. Vite, for example, wants it in `server.allowedHosts`. See [Dev servers and hot reload](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/). ## Check it works Start the project with `nearhost up`, or from the interface, and open `https://local.myapp.com`. The page should load, Clerk’s sign-in button should appear, and signing in should bring you back signed in. Edit a component, and the page should update without a reload. When it does not: * **The page loads, but edits do not show until you reload.** Next.js is blocking hot reload from the new name. The server log shows `Blocked cross-origin request to Next.js dev resource` with the hostname it saw. Add that hostname to `allowedDevOrigins` and restart `next dev`. * **You sign in, but come back signed out, or requests return 401.** If `clerkMiddleware()` has `authorizedParties`, check that it lists `https://local.myapp.com` exactly, with `https` and no port. Check too that the publishable and secret keys come from the same instance. * **Links or redirects you build yourself go to `localhost`.** They come from an environment variable that still says `http://localhost:3000`. Change it to `https://local.myapp.com`. ## Testing with production keys Clerk’s production keys only work on your production domain. Clerk describes a way round that for debugging, with a local subdomain over HTTPS on port 443, which Nearhost provides, but calls it strongly discouraged. See [using production keys in local development](https://clerk.com/docs/guides/development/troubleshooting/using-production-keys-in-development). ## When you still need ngrok Nearhost is local-only. The name works in your browser on your laptop, and nowhere else. Use a public tunnel when: * **Clerk sends webhooks.** Clerk sends them through Svix, from its servers, which cannot reach your laptop. Point the endpoint on the dashboard’s **Webhooks** page at a tunnel to the server, such as `https://<your-tunnel>/api/webhooks`. Clerk’s CLI also has `clerk webhooks listen --forward-to`, a relay that forwards deliveries to a local URL. Run it on the server, next to the app. * **Someone outside needs the link.** A colleague or a client cannot open `local.myapp.com` from their machine. You can run both: Nearhost for your own browser, and a tunnel just for the webhook endpoint.

# Cognito sign-in on a remote dev server

> Give an Amazon Cognito app client an HTTPS callback URL in local dev, such as https://local.myapp.com/auth/cognito/callback, when the dev server runs on another machine.

New to Nearhost? [Install it](/pr-preview/pr-96/docs/getting-started/install/) and [add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) first. This guide gets Amazon Cognito sign-in working at `https://local.myapp.com` while your Laravel app runs on another machine. The worked example uses Laravel Socialite with the community `socialiteproviders/cognito` provider and Cognito’s managed login pages. The Cognito and Nearhost steps are the same for any stack. ## The symptom Cognito sends the browser back to your app at a callback URL you list on the app client. Every callback URL has to use HTTPS, with one exception: `http://localhost`, which Cognito allows for testing. When the app runs on your laptop, that exception is all you need. When the app runs on a server or a VM, `localhost` in your browser is not where the app is. You can forward a port with `ssh -L` and use `http://localhost:8080`, and for one app that works. It stops being enough when: * **You run more than one app.** Browsers do not separate cookies by port, so two apps on `localhost` can overwrite each other’s session cookies. * **The app shares cookies across subdomains.** An app that sets cookies for `myapp.com`, or talks to an API on another subdomain, only behaves as it does on staging when it runs under that domain. * **You want local dev to match staging.** Staging’s callback is HTTPS on your domain. With `http://localhost`, the scheme, the host and the cookie rules all differ from what you deploy. * **The page uses browser APIs that need a secure context**, such as service workers or the clipboard. Browsers count `http://localhost` as secure, so these work there, but on any other name, such as the server’s own address, they need HTTPS. A tunnel such as ngrok gives you HTTPS, but each new tunnel name is one more callback URL to add, and the app still builds its links from its own idea of where it lives. It also puts the app on the public internet while you work on it. Nearhost serves the remote app on your laptop at a name you choose, with a trusted certificate, over SSH. The browser sees one stable HTTPS origin, and that is the origin you list on the Cognito app client. ## Pick a name Use a name under a domain you own, such as `local.myapp.com`. It needs no DNS record: Nearhost points it at your laptop through `/etc/hosts` while the project is enabled. When the project is disabled, the name resolves as it normally would. A real-domain name keeps the callback URL shaped like the one on staging and in production. Cognito’s documentation asks for HTTPS but does not say whether it accepts `.test` names, so this guide uses a domain you own. ## Add the project On the command line, give the name with `--alias`: 
```sh
nearhost add --server mini '~/code/myapp' --alias local.myapp.com
```
 
```text
Added myapp on mini at https://local.myapp.com
Start it with `nearhost up`.
```
 A name that does not end in `.test` needs your approval, because it can hide the real site. Typing it with `--alias` counts as approval. To keep the name with the project, put it in a [`.nearhostrc`](/pr-preview/pr-96/docs/reference/nearhostrc/) in the project’s root: 
```yaml
version: 1
alias: local.myapp.com
```
 Run `nearhost add` without `--alias`, and it asks before using the name, since you did not type it: 
```text
$ nearhost add --server mini '~/code/myapp'
This project asks for these, which need your approval:
  local.myapp.com on port 8080 (a real domain)
Approve these? [y/N]
```
 See [Add a project](/pr-preview/pr-96/docs/getting-started/add-a-project/) for the rest of the add flow, and [Main name](/pr-preview/pr-96/docs/reference/config/#main-name) for how the name is approved and written to the hosts file. ## Set up Cognito Use a user pool for development, separate from production’s. Its users, app clients and settings are its own. 1. The pool needs a domain for its sign-in pages. In the [Amazon Cognito console](https://console.aws.amazon.com/cognito/home), open the user pool, then **Domain** under **Branding**. If there is no domain, choose **Actions**, then **Create Cognito domain**, and pick a prefix. The domain looks like `https://myapp-dev.auth.eu-west-2.amazoncognito.com`. Either branding version, **Managed login** or **Hosted UI (classic)**, works for this guide. 2. Open **App clients** and create an app client with the application type **Traditional web application**. That type gives the client a secret, which Socialite needs. You cannot add a secret to an existing client later, so if yours has none, create a new one. When it asks for a **Return URL**, enter `https://local.myapp.com/auth/cognito/callback`. 3. Open the app client, then the **Login pages** tab. Under **Managed login pages configuration**, choose **Edit**. 4. Check that **Allowed callback URLs** has `https://local.myapp.com/auth/cognito/callback`. It must match the URL your app sends exactly: `https`, the host, the path, no trailing slash. 5. Add `https://local.myapp.com/` to **Allowed sign-out URLs**. Cognito only sends people back after sign-out to a URL on this list. 6. Under **Identity providers**, keep the user pool’s own sign-in, or whichever providers your users sign in with. Under **OAuth grant types**, choose **Authorization code grant**. Under **OpenID Connect scopes**, choose `openid`, `email` and `profile`. Save the changes. Then set `APP_URL` in the app’s `.env` to the new name, and copy the domain and the app client’s ID and secret below it. The last two lines build on `APP_URL`, so they have to come after it: 
```ini
APP_URL=https://local.myapp.com


COGNITO_HOST=https://myapp-dev.auth.eu-west-2.amazoncognito.com
COGNITO_CLIENT_ID=your-client-id
COGNITO_CLIENT_SECRET=your-client-secret
COGNITO_CALLBACK_URL="${APP_URL}/auth/cognito/callback"
COGNITO_SIGN_OUT_URL="${APP_URL}/"
```
 These are the names in the provider’s README. `COGNITO_HOST` is the full domain with `https://` and no trailing slash. ## Set up the app Install the provider, which brings in Socialite: 
```sh
composer require socialiteproviders/cognito
```
 Add the Cognito entry to `config/services.php`: 
```php
'cognito' => [
    'host' => env('COGNITO_HOST'),
    'client_id' => env('COGNITO_CLIENT_ID'),
    'client_secret' => env('COGNITO_CLIENT_SECRET'),
    'redirect' => env('COGNITO_CALLBACK_URL'),
    'logout_uri' => env('COGNITO_SIGN_OUT_URL'),
],
```
 The README’s version also has a `scope` line. The provider does not read it, so this guide sets scopes in code instead. Register the provider in the `boot` method of `app/Providers/AppServiceProvider.php` (Laravel 11 and later): 
```php
use Illuminate\Support\Facades\Event;
use SocialiteProviders\Cognito\Provider;
use SocialiteProviders\Manager\SocialiteWasCalled;


public function boot(): void
{
    Event::listen(function (SocialiteWasCalled $event) {
        $event->extendSocialite('cognito', Provider::class);
    });
}
```
 Then add the routes to `routes/web.php`. The provider asks for `openid` and `profile` by default; `scopes()` adds `email` to them: 
```php
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Auth;
use Illuminate\Support\Facades\Route;
use Laravel\Socialite\Socialite;


Route::get('/auth/cognito/redirect', function () {
    return Socialite::driver('cognito')->scopes(['email'])->redirect();
});


Route::get('/auth/cognito/callback', function () {
    $cognitoUser = Socialite::driver('cognito')->user();


    // Find or create your user from $cognitoUser, then Auth::login($user).


    return redirect('/dashboard');
});


Route::post('/auth/cognito/logout', function (Request $request) {
    Auth::logout();


    $request->session()->invalidate();
    $request->session()->regenerateToken();


    return redirect(Socialite::driver('cognito')->logoutCognitoUser());
});
```
 `logoutCognitoUser()` sends the browser to Cognito’s sign-out page with `COGNITO_SIGN_OUT_URL`, and Cognito sends it back there. With `APP_URL` set to `https://local.myapp.com`, the callback and sign-out URLs follow it. If you have cached the config, run `php artisan config:clear`. Nearhost’s proxy ends HTTPS on your laptop and passes plain HTTP to the server, with `X-Forwarded-Proto: https`. Laravel ignores that header until it trusts the proxy, so it thinks the request was `http://`. The callback is unaffected while `COGNITO_CALLBACK_URL` is a full URL, because Socialite uses it as it is. A path such as `/auth/cognito/callback` would be built from the request instead, as `http://`, and Cognito would refuse it. What goes wrong either way is everything Laravel builds from the request: `route()` and `url()` links, the redirect to `/dashboard` after sign-in, and `asset()` URLs. The fix is one line in the `withMiddleware` closure in `bootstrap/app.php`: 
```php
$middleware->trustProxies(at: '*');
```
 The [WorkOS guide](/pr-preview/pr-96/docs/guides/workos-sign-in/#set-up-the-app) explains it, and what to list instead of `'*'` if the file also runs in production behind a known load balancer. If the page loads its scripts from Vite at `http://localhost:5173`, that port needs a `loopback` route so your browser can reach it. See [Dev servers and hot reload](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/). If `public/hot` says `http://[::1]:5173` instead, the forward answers there too from Nearhost 0.7.0. With an older Nearhost, see [Vite on `[::1]`](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/#vite-on-1). On another stack the idea is the same. Use any OpenID Connect client with the pool’s domain and the app client’s ID and secret. Set the app’s public URL and its callback URL to `https://local.myapp.com`, and tell the framework to trust `X-Forwarded-Proto` from the proxy, so it builds `https://` links and the callback URL it sends to Cognito matches the one you listed. ## Check it works Start the project with `nearhost up`, or from the interface, and open `https://local.myapp.com/auth/cognito/redirect`. You should land on Cognito’s sign-in page, and after signing in come back to `https://local.myapp.com/auth/cognito/callback` and on to the dashboard. When it does not: * **Cognito shows an error page instead of the sign-in page.** Usually the callback URL your app sent is not in **Allowed callback URLs** on the app client whose ID you use. Compare them character by character: `https`, the host, `/auth/cognito/callback`, no trailing slash. Check that `COGNITO_CALLBACK_URL` and `APP_URL` are what you expect. * **You come back with `error=invalid_scope` in the address.** The app asked for a scope the app client does not allow. Add `openid`, `email` and `profile` under **OpenID Connect scopes**, or ask for fewer. * **The callback fails with `InvalidStateException`.** Socialite keeps a state value in the session when you start sign-in, and refuses the callback when the session does not come back with it. Start sign-in at `https://local.myapp.com`, not at another address for the same app, and leave `SESSION_DOMAIN` unset (`null`) or set it to `local.myapp.com`. A cookie set for another domain never reaches this one. * **Links, the redirect after sign-in, or asset URLs use `http://`.** Laravel does not trust the proxy yet. Add `trustProxies` as above. Nearhost redirects `http://` to HTTPS, so a link may still seem to work, but `http://` scripts and styles on an HTTPS page are blocked as mixed content. Look for those warnings in the console. * **Sign-out does not come back to `https://local.myapp.com/`.** Cognito only redirects to a URL in **Allowed sign-out URLs**. Check that `COGNITO_SIGN_OUT_URL` is on that list exactly, trailing slash included. ## When you still need ngrok Nearhost is local-only. The name works in your browser on your laptop, and nowhere else. Cognito itself does not need to reach your app. The browser carries the sign-in there and back, and your server calls Cognito, not the other way round. Cognito’s hooks into sign-up and sign-in are Lambda triggers, which run in AWS, not webhooks sent to your app. Use a public tunnel when: * **Something in AWS calls your app.** A Lambda trigger, or anything else running in AWS, cannot reach your laptop or your dev server. If a trigger calls your app’s API, point it at a tunnel. * **Someone outside needs the link.** A colleague or a client cannot open `local.myapp.com` from their machine. You can run both: Nearhost for your own browser, and a tunnel just for whatever AWS has to call.

# Callbacks from Docker containers to a local HTTPS domain

> Let a Docker Compose service, such as a queue worker or a LocalStack job, call your app at its Nearhost HTTPS name on this machine.

A service in your Compose file often calls the app back: a queue worker reports a finished job, or a LocalStack job delivers an event to a webhook. Point it at the app’s Nearhost name, such as `https://api.local.example.com/webhooks/jobs`, and the call fails, even though the same URL works in your browser. Three things stand between the container and Nearhost. The container cannot find the host, it does not trust the local certificate authority, and on Linux Nearhost does not let it in. The fixes go in the project’s files, which you commit. Each developer then sets one variable, for the certificate’s path, and approves the opt-in on their own machine. This works only for a project on this machine. A container on an SSH server cannot reach the proxy on your laptop. ## The example The project is named `shop`, and its worker is a Node service. Its app listens on port 8000 and is served at `api.local.example.com`. Its `.nearhostrc`: 
```yaml
version: 1
routes:
  - port: ${APP_PORT:-8000}
    label: app
    hosts: [api.local.example.com]
docker_clients: true
```
 `hosts` serves the route at a name of your own, besides the project’s main name. See [Multi-host projects](/pr-preview/pr-96/docs/concepts/multi-host-projects/). `docker_clients` is explained in [Being let in](#being-let-in). Its Compose file runs the app and a worker that calls it: 
```yaml
services:
  app:
    build: .
    ports:
      - '${APP_PORT:-8000}:8000'
  worker:
    build: .
    command: ['./worker']
    environment:
      WEBHOOK_URL: https://api.local.example.com/webhooks/jobs
```
 Nothing here depends on the stack. Any service that reads a URL naming a host Nearhost serves, from its `environment`, its `env_file` files, or the project’s `.env` or `.env.local` when it mounts the project directory, has the same three problems. ## Reaching the host Nearhost puts `api.local.example.com` in your machine’s [hosts file](/pr-preview/pr-96/docs/concepts/the-hosts-file/), pointing at loopback. A container does not read that file, and inside it loopback is the container itself. So the name resolves to nothing, to the public internet, or, where DNS points it at 127.0.0.1, back to the container. Map the name to the host with `extra_hosts`. `host-gateway` is Docker’s name for the host’s address as seen from a container: 
```yaml
services:
  worker:
    extra_hosts:
      - 'api.local.example.com:host-gateway'
```
 List every name the service calls. `nearhost doctor` reports a service that calls a name without this mapping, as `docker.host-gateway`, and its fix is this snippet for the names it found. ## Trusting the local CA Nearhost’s certificates are signed by its own local certificate authority. Your system trusts it, but a container has its own trust store, so the call fails with a certificate error. Mount the root certificate into the container and point the service at it. The certificate is at `pki/authorities/local/root.crt` under Nearhost’s `caddy` folder, which is `~/Library/Application Support/nearhost/caddy` on macOS and `~/.local/share/nearhost/caddy` on Linux, or `$XDG_DATA_HOME/nearhost/caddy` on either when that is set to an absolute path. `nearhost doctor` prints the path on your machine. Earlier versions kept it under `~/.config/nearhost/caddy`, or `$XDG_CONFIG_HOME/nearhost/caddy` when that variable was set. Nearhost 0.8.0 moves that folder the first time it runs while no other Nearhost is running. After that, a `NEARHOST_CA_CERT` set for an earlier version points at a file that is gone, so set it to the new path, which `nearhost doctor` prints. Mount only `root.crt`, never the folder: the key is beside it. The doctor’s snippet, for a Node service: 
```yaml
services:
  worker:
    environment:
      NODE_EXTRA_CA_CERTS: /usr/local/share/ca-certificates/nearhost.crt
    volumes:
      - "${NEARHOST_CA_CERT:?set NEARHOST_CA_CERT to Nearhost's root certificate}:/usr/local/share/ca-certificates/nearhost.crt:ro"
```
 Each developer sets `NEARHOST_CA_CERT` to the certificate’s path in their shell profile, or in `.env` when the project does not commit `.env`, so the Compose file holds no one’s path. Compose reads only `.env` and the shell, not `.env.local`. Until the variable is set, every `docker compose` command that reads this Compose file stops with `set NEARHOST_CA_CERT to Nearhost's root certificate`, so nobody runs the service without the certificate by mistake. `NODE_EXTRA_CA_CERTS` adds the certificate to Node’s own. `SSL_CERT_FILE`, `AWS_CA_BUNDLE` and `REQUESTS_CA_BUNDLE` replace the default bundle instead, so point them at a bundle that includes the certificate, or have the image run `update-ca-certificates`. `nearhost doctor` reports a service that calls a name Nearhost serves and does not trust the certificate, as `docker.ca`. A service that sets `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `AWS_CA_BUNDLE`, `REQUESTS_CA_BUNDLE` or `CURL_CA_BUNDLE`, or mounts the certificate’s path, counts as set up. The doctor checks only that the setting is there, not that the runtime trusts the certificate, so a worker in another language needs the setting its runtime reads. ## Being let in Nearhost serves its projects only to this machine. A request from anywhere else is dropped without an answer. On Linux, a container’s request comes from its address on a Docker network, not from loopback, so Nearhost drops it. `docker_clients: true` in the project’s [`.nearhostrc`](/pr-preview/pr-96/docs/reference/nearhostrc/#docker-clients) serves the project to the networks the Docker daemon has on this machine as well. Nearhost asks Docker for them when the project starts, and again every 30 seconds while it runs, so a network Compose creates later is let in too. It finds Docker through `DOCKER_HOST` or the current docker context, then the usual sockets of Docker Desktop, OrbStack, Rancher Desktop, Colima and Podman. From Nearhost 0.8.0. Until Docker first answers, it accepts requests from `172.16.0.0/12`, the private block most of Docker’s default networks come from, which can also take in other machines on that block your machine can reach. The project’s log says which networks it accepts requests from. * It works only for a project on this machine. On a project on a server, the file is an error. * It always needs your approval, as a real domain does. See [Approval](/pr-preview/pr-96/docs/reference/nearhostrc/#approval). * Other projects stay loopback-only. Only the project that opts in is served to Docker’s networks. With no `.nearhostrc` yet, `nearhost export` writes one from the project’s current setup, and you add the line to it. Docker Desktop on macOS already delivers container requests from 127.0.0.1, so this matters on Linux. On a Mac, the project is reached without it. Keep it in a committed `.nearhostrc` if anyone on the team uses Linux. `nearhost doctor` reports a project whose containers call a name it serves without the opt-in, as `docker.clients`. It is a warning on Linux, and only a note on macOS. ## The finished Compose file 
```yaml
services:
  app:
    build: .
    ports:
      - '${APP_PORT:-8000}:8000'
  worker:
    build: .
    command: ['./worker']
    environment:
      WEBHOOK_URL: https://api.local.example.com/webhooks/jobs
      NODE_EXTRA_CA_CERTS: /usr/local/share/ca-certificates/nearhost.crt
    extra_hosts:
      - 'api.local.example.com:host-gateway'
    volumes:
      - "${NEARHOST_CA_CERT:?set NEARHOST_CA_CERT to Nearhost's root certificate}:/usr/local/share/ca-certificates/nearhost.crt:ro"
```
 Approve `api.local.example.com` and `docker_clients` when you add the project, or when Nearhost asks after the file changes. See [Approval](/pr-preview/pr-96/docs/reference/nearhostrc/#approval). Then restart the worker with `docker compose up -d worker`. ## Check it works Run `nearhost doctor`. After the machine checks, it lists what it finds in each enabled project. For the example before any of the fixes, with `docker_clients` not yet in its `.nearhostrc`, on a Mac, these are the first lines of its three findings, without their fixes: 
```text

warn  shop             worker uses api.local.example.com, which a container resolves to itself or to the public internet, not to Nearhost

```
 Under each, a `fix:` line says what to do, followed by the snippet to paste. These are `docker.ca`, `docker.host-gateway` and `docker.clients`, and `nearhost doctor --json` gives each finding’s `id`. On Linux the last one is a warning too. When the project is fixed, none of them is shown. See [nearhost doctor](/pr-preview/pr-96/docs/reference/cli/#nearhost-doctor). The doctor only reads the files. To see the call work, run the worker and watch the request arrive in Nearhost. ## When a public tunnel is still the right tool This is for services you run yourself, on this machine. A webhook from a real provider, such as a payment or source control service, comes from its servers, which cannot reach your laptop. Use a public tunnel, such as ngrok, for that. # Forward several ports over SSH without retyping -L

> Ways to reach a remote app, its asset server and its other ports from your laptop over SSH, from stacked -L flags to forwards added to a running connection, and what each leaves for you to do.

A web project on a remote machine rarely uses one port. There is the app, the asset dev server, perhaps a mail catcher or a queue dashboard, and the next project wants the same set again. Typing one `-L` flag per port works until the connection drops, a port changes, or a second project needs a port the first one already holds. ## Stack the flags on one connection One `ssh` command takes as many `-L` flags as you need. `-N` keeps it to forwarding, with no remote shell: 
```sh
ssh -N -L 8000:localhost:8000 -L 5173:localhost:5173 -L 8025:localhost:8025 myserver
```
 Each flag reads `local port:host:remote port`, and the host is resolved on the server, so `localhost` means the server itself. Your laptop listens on loopback only, unless you set `GatewayPorts`. ## Put them in your SSH config `LocalForward` lines in `~/.ssh/config` set the same forwards whenever you connect: 
```plaintext
Host myserver
  LocalForward 8000 localhost:8000
  LocalForward 5173 localhost:5173
  LocalForward 8025 localhost:8025
  ExitOnForwardFailure yes
  ServerAliveInterval 15
```
 `ExitOnForwardFailure` makes `ssh` stop when a port is taken on your laptop, rather than connect without that forward. `ServerAliveInterval` makes a dead connection end, after about 45 seconds with the default `ServerAliveCountMax` of 3, instead of hanging. The catch: every interactive `ssh myserver` now tries the same ports, and the second one fails while the first is open. A separate `Host` alias just for the forwards avoids that. ## Add forwards to a running connection With connection sharing, one master connection carries every session to a server, and `ssh -O` changes its forwards while it runs: 
```plaintext
Host myserver
  ControlMaster auto
  ControlPath ~/.ssh/cm-%C
  ControlPersist 10m
```
 
```sh
ssh -O forward -L 5173:localhost:5173 myserver   # add a forward
ssh -O cancel -L 5173:localhost:5173 myserver    # remove it
```
 No reconnect, and no restart of the forwards already open. Nothing re-adds them if the master exits, though. ## Use one SOCKS proxy instead `ssh -N -D 1080 myserver` opens a SOCKS proxy, and a browser set to use it reaches every port on the server’s network. But Chrome and Firefox send `localhost` straight to your own machine, never through the proxy, so a dev server that listens only on the server’s loopback stays out of reach. It also proxies every site the browser opens, unless you set it per profile. ## What every plain-SSH option leaves to you * **Reconnecting.** When the connection drops, the forwards go with it. `autossh` or a shell loop brings back a fixed set. * **Port clashes.** Two projects that both use 5173 cannot both forward it to 5173 on your laptop. Change one project’s port, or forward it to another local port where the page does not hard-code it. * **The address.** Each app is `http://localhost:<port>`. Cookies ignore the port, so every project shares one cookie jar and signing in to one can sign you out of another, and an OAuth callback or cookie domain set up for a real name does not match. See [HTTPS on a local dev domain](/pr-preview/pr-96/docs/guides/https-on-a-local-dev-domain/). ## How Nearhost does it New to Nearhost? [Install it](/pr-preview/pr-96/docs/getting-started/install/) and [add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) first. Nearhost uses the same OpenSSH mechanism as above: one supervised master per server, with forwards added and cancelled with `-O forward` and `-O cancel` as projects start and stop. On top of that: * **It finds the ports.** It reads them from the project’s `.env`, and presets add Docker Compose, Vite and Laravel Sail. You choose which port is the web app, which need the same port on your laptop, and which to ignore. * **It reconnects.** If the master exits, Nearhost starts it again with backoff and puts every forward back before the server shows as connected. * **It warns about clashes** before they happen, and suggests a free port when the port comes from a variable. * **It gives each project a name.** The web port is served at a trusted `https://myapp.test`, so you stop tracking which port is which project. See [SSH transport](/pr-preview/pr-96/docs/concepts/ssh-transport/) for the exact commands it runs, and [Routes and roles](/pr-preview/pr-96/docs/concepts/routes-and-roles/) for how ports become routes.

# HTTPS on a local dev domain

> Serve local development at a trusted HTTPS name, such as myapp.test or local.myapp.com, so secure-context browser APIs and Secure cookies work, and choose which kind of name to use.

Some things in local development only work over HTTPS. On your laptop you rarely notice, because browsers treat `http://localhost` as secure. Once you browse to the dev server by its address or by a name instead of `localhost`, which is usual when it runs on another machine, plain HTTP stops being enough. ## What needs HTTPS Browsers give some features only to a secure context: a page served over HTTPS, or from `localhost`, `127.0.0.1` or a `*.localhost` name. On `http://192.168.1.20:8080` or `http://myapp.test`, these are missing: * **Service workers.** `navigator.serviceWorker` is undefined, so offline support and push notifications cannot be tested. * **The clipboard.** `navigator.clipboard` is undefined, so copy buttons fail. * **Web Crypto.** `crypto.subtle` is undefined, which breaks libraries that hash or sign in the browser. * **The camera and microphone.** `navigator.mediaDevices` is undefined. * **Passkeys and geolocation.** WebAuthn and the Geolocation API refuse to run. Cookies have the same rule. Browsers do not set a cookie marked `Secure` over plain HTTP. Chrome and Firefox make an exception for `localhost`, but Safari does not, so test secure cookies over HTTPS. That rules out `SameSite=None` cookies, which must be `Secure`, and the `__Host-` and `__Secure-` cookie prefixes. If your app sets these in production, it behaves differently in development without HTTPS. A self-signed certificate is not a fix. The browser warns on every visit, and some features, such as service workers, refuse to load over a certificate it does not trust. ## Choosing a name You need a name the browser resolves to the dev server, and a certificate for it that the browser trusts. **A `.test` name, such as `myapp.test`.** `.test` is reserved for testing and never exists on the public internet, so it cannot clash with a real site. It is Nearhost’s default, and works with no setup. Some third-party services, such as sign-in providers, may not accept a `.test` callback, or do not say whether they do. **A name under your own domain, such as `local.myapp.com`.** It is shaped like production, so cookie scoping, cross-subdomain requests and provider settings behave as they do on staging. It needs no DNS record. Two things to know: * Cookies your production site sets for the whole domain, with `Domain=myapp.com`, are sent to `local.myapp.com` too, if your browser has them. * Nearhost writes the name to `/etc/hosts` only while the project is enabled. Disable the project, and the name reaches the real site again, if there is one. See [Main name](/pr-preview/pr-96/docs/reference/config/#main-name). Avoid `.dev`, which is a real top-level domain whose every name browsers force to HTTPS, and `.local`, which macOS and many Linux systems resolve with multicast DNS, and which can be slow to look up. ## Setting it up If the dev server runs on your laptop, a tool such as mkcert and a line in `/etc/hosts` are enough. You make a local certificate authority, trust it, issue a certificate for the name, and point the dev server at it. If the dev server runs on another machine, Nearhost does all of this on your laptop. It creates a local certificate authority the first time it starts, which you trust once with your password, and it issues a certificate for each project’s name. Its proxy serves the name over HTTPS and forwards to the dev server over SSH. See [TLS and the proxy](/pr-preview/pr-96/docs/concepts/tls-and-the-proxy/). New to Nearhost? [Install it](/pr-preview/pr-96/docs/getting-started/install/) and [add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) first. Add the project with the name you chose: 
```sh
nearhost add --server mini '~/code/myapp' --alias local.myapp.com
```
 Leave out `--alias` to use `myapp.test`. Then tell the app it lives at the HTTPS name: set its public URL, such as `APP_URL`, and trust the proxy’s `X-Forwarded-Proto` header. The [WorkOS guide](/pr-preview/pr-96/docs/guides/workos-sign-in/#set-up-the-app) shows both for Laravel. Single-port dev servers also need the name allowed: `allowedDevOrigins` in Next.js, `server.allowedHosts` in Vite. See [Dev servers and hot reload](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/). ## Sign-in providers Sign-in providers are the most common reason to want a real HTTPS name. The guides set one up end to end: * [WorkOS sign-in](/pr-preview/pr-96/docs/guides/workos-sign-in/) * [Clerk sign-in](/pr-preview/pr-96/docs/guides/clerk-sign-in/) * [Cognito sign-in](/pr-preview/pr-96/docs/guides/cognito-sign-in/) If the callback is what fails, see [SSO callback fails on a remote dev server](/pr-preview/pr-96/docs/guides/sso-callback-on-a-remote-dev-server/). ## When ngrok is still the right tool A Nearhost name only works on your laptop. Its proxy answers no other machine. Use a public tunnel, such as ngrok, when: * **Another device needs the page,** such as your phone, to test a camera or a service worker on mobile. * **Someone outside needs the link,** such as a colleague or a client. * **A service sends webhooks,** from servers that cannot reach your laptop.

# ngrok loads the page, but assets point at localhost

> Why a dev site behind ngrok still loads its scripts, redirects or hot reload from localhost or http://, how to patch each one, and how to skip the tunnel when the dev server runs on another machine.

You put your dev server behind ngrok and open the tunnel’s address. The HTML arrives, and then something still points somewhere else: the scripts and styles try `localhost`, a redirect takes you to `http://localhost:8000`, or the page never updates when you edit a file. Sometimes the dev server refuses the request outright. The tunnel did its job. It forwarded the request. The problem is that the page and the dev server still describe themselves with the addresses in their own config, and those addresses mean nothing in the browser that opened the tunnel. ## Why it happens Three different things build URLs, and each one gets it wrong in its own way. ### The asset dev server A backend framework that uses Vite renders the HTML itself, and the page loads its scripts from the Vite dev server on a separate port. In Laravel, the `@vite` directive reads the `public/hot` file, which `laravel-vite-plugin` writes when `npm run dev` starts. That file holds the dev server’s own address, such as `http://localhost:5173` under Sail or `http://[::1]:5173` elsewhere, and every script tag on the page points there. Your browser resolves that address on your laptop. If the dev server runs on another machine, nothing listens there, so scripts and styles fail to load and hot reload never connects. Even where something does answer, the Vite dev server only allows requests from the origins `laravel-vite-plugin` lists: `localhost`, `*.test`, `*.localhost` and your `APP_URL`. An ngrok address is none of them unless you put it in `APP_URL`. Rails, Django and other backends that pair with Vite work the same way. ### Links and redirects Most frameworks build absolute URLs from the request, or from a URL in their config. * **From the request.** ngrok ends HTTPS at its edge and forwards to your dev server, adding `X-Forwarded-Proto: https`. A framework that does not trust the proxy ignores that header and builds `http://` links and redirects. If you started ngrok with `--host-header=rewrite`, the app sees the local address’s hostname, usually `localhost`, and builds links to that. * **From config.** Anything built from `APP_URL` or a similar setting, such as emails, queued jobs, or an OAuth redirect URI, uses whatever that setting says, usually `http://localhost:8000`. ### Host checks in single-port dev servers Next.js and plain Vite serve pages, assets and hot reload from one port, so their assets use relative paths. What gets in the way is the dev server’s host check: * **Next.js** serves the page, assets included. Recent versions block its dev resources, hot reload included, from hostnames it was not told about, and log `Blocked cross-origin request to Next.js dev resource` on the server. The page loads, but edits never show. * **Vite** refuses every request whose `Host` it does not recognise, the page included, and answers with `Blocked request. This host ("…") is not allowed.`, naming the host. Nothing loads until the host is in `server.allowedHosts`. ## Patching it with ngrok Each patch fixes one of the three. * **Assets.** Stop the dev server, which deletes `public/hot`, and run `npm run build`. Laravel then serves the built files from the app’s own origin. You lose hot reload. On other backends, build the assets or tunnel the Vite port. Keeping hot reload means a second tunnel for port 5173, with Vite told to advertise that tunnel’s address through `server.origin` and `server.hmr`, and that tunnel’s hostname added to `server.allowedHosts`. Once `server.origin` is set, Laravel’s Vite plugin allows only that origin through CORS, so also set `server.cors.origin` to the app tunnel’s address, or the browser blocks the scripts. * **Links and redirects.** Set `APP_URL` to the tunnel’s address and make the framework trust the proxy. The [WorkOS guide](/pr-preview/pr-96/docs/guides/workos-sign-in/#set-up-the-app) shows the one-line `trustProxies` change for Laravel. If the tunnel name changes each time you start it, so does `APP_URL`. * **Host checks.** Add the tunnel’s hostname to `allowedDevOrigins` in `next.config.ts`, or to `server.allowedHosts` in Vite’s config. ## How Nearhost avoids it New to Nearhost? [Install it](/pr-preview/pr-96/docs/getting-started/install/) and [add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) first. When the dev server runs on another machine, Nearhost serves it on your laptop at a name such as `https://myapp.test`, with a trusted certificate, over SSH. Nothing is public, and the name stays the same every time. * **Assets.** A `loopback` route forwards the Vite port, so `http://localhost:5173` in your browser reaches port 5173 on the remote machine. `.test` names are already on the Vite dev server’s allowed origins. Under Laravel Sail, Nearhost proposes the route for you. See [Dev servers and hot reload](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/). * **Links and redirects.** The proxy passes the `Host` header through unchanged and sets `X-Forwarded-Proto: https`. Set `APP_URL` to the Nearhost name once, and trust the proxy as above. * **Host checks.** Add the Nearhost name to `allowedDevOrigins` or `server.allowedHosts` once. It does not change between runs. ### Vite on the IPv6 loopback address A Vite dev server that listens on `::1` makes `laravel-vite-plugin` write `http://[::1]:5173` to `public/hot`. A loopback forward answers on both `127.0.0.1` and `[::1]`, so that works as it is. This needs Nearhost 0.7.0 or later and a laptop with the IPv6 loopback, which every Mac and almost every Linux machine has. Otherwise, see [Vite on `[::1]`](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/#vite-on-1). ## The guides The sign-in guides walk through all of this for one app each, at a name under your own domain: * [WorkOS sign-in](/pr-preview/pr-96/docs/guides/workos-sign-in/), with Laravel * [Clerk sign-in](/pr-preview/pr-96/docs/guides/clerk-sign-in/), with Next.js * [Cognito sign-in](/pr-preview/pr-96/docs/guides/cognito-sign-in/), with Laravel ## When ngrok is still the right tool Nearhost only answers your own laptop. Keep a tunnel for: * **Webhooks.** A payment provider, an auth provider or GitHub sends them from its own servers, which cannot reach your laptop. * **Sharing a link.** A colleague, a client, or your phone cannot open a Nearhost name. You can run both: Nearhost for your own browser, and a tunnel for the one endpoint that the outside world has to reach.

# SSO callback fails on a remote dev server

> Why an SSO or OAuth sign-in callback fails, or lands on localhost or the wrong origin, when your dev server runs on a server or VM, and how to give it one HTTPS address that works.

Sign-in works when the app runs on your laptop. Move the dev server to a server or a VM, and it falls apart: the provider shows a redirect URI error, or you sign in and land on `localhost` with nothing there, or you come back to the app and it says the sign-in state is invalid. ## Why it happens Sign-in with an SSO or OAuth provider is a round trip through your browser. The app sends the browser to the provider with a callback URL. The provider checks that URL against the list you registered, and after sign-in sends the browser back to it. The callback has to be right three times over: the app has to send it, the provider has to accept it, and your browser has to reach the app at it. A remote dev server breaks one of those, depending on the address you use. * **`http://localhost`.** Most providers accept it for development, and the app sends it happily. But your browser resolves `localhost` on your laptop, so after sign-in it lands where nothing is listening. Forwarding the port with `ssh -L` fixes that for one app. * **The server’s own address,** such as `http://192.168.1.20:8080`. The browser reaches it, but providers that allow plain HTTP usually allow it only for `localhost`. Cognito, for example, requires HTTPS for every other callback. * **A tunnel,** such as ngrok. It gives you HTTPS, but each new tunnel name is one more callback to register, and the app still builds its callback from its own config. If that says `http://localhost`, or the app does not trust the tunnel and builds `http://`, the URL it sends does not match the one you registered. See [ngrok loads the page, but assets point at localhost](/pr-preview/pr-96/docs/guides/ngrok-assets-on-localhost/). There is a fourth failure that looks the same. Most integrations store a state value in a session cookie when sign-in starts, and check it on the callback. If you start sign-in at one address and come back at another, the cookie does not come with you, and the callback is refused. In Laravel, `laravel/workos` answers with a 403, and Socialite throws an `InvalidStateException`. ## The fix: one HTTPS address everywhere New to Nearhost? [Install it](/pr-preview/pr-96/docs/getting-started/install/) and [add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) first. Pick one address and use it in all three places: the URL your browser opens, the callback the app sends, and the callback the provider has registered. It has to be HTTPS, and your browser has to reach the remote app at it. Nearhost gives you that address. It serves the remote dev server on your laptop at a name you choose, such as `https://local.myapp.com`, with a trusted certificate, over SSH. Add the project with that name: 
```sh
nearhost add --server mini '~/code/myapp' --alias local.myapp.com
```
 Then, on the app and provider side: 1. **Register the callback** with the provider, on that name: for example `https://local.myapp.com/auth/callback`. Use the provider’s development or staging environment. 2. **Set the app’s public URL** to `https://local.myapp.com`, in `APP_URL` or whatever your framework reads, so the callback the app sends matches. 3. **Trust the proxy.** Nearhost ends HTTPS on your laptop and sets `X-Forwarded-Proto: https`. A framework that ignores the header builds `http://` links and redirects. In Laravel, that is one `trustProxies` line; the [WorkOS guide](/pr-preview/pr-96/docs/guides/workos-sign-in/#set-up-the-app) shows it. 4. **Start sign-in at the same name.** Open `https://local.myapp.com`, not the server’s address or an old tunnel, so the state cookie comes back. ## The guides Each provider has its own setup, and its own way of failing. The guides cover them step by step: * [WorkOS sign-in](/pr-preview/pr-96/docs/guides/workos-sign-in/): the redirect URI on the **Redirects** tab, with Laravel and `laravel/workos`. * [Clerk sign-in](/pr-preview/pr-96/docs/guides/clerk-sign-in/): a development instance needs no callback registered at all, and what breaks is the dev server’s hot reload. With Next.js. * [Cognito sign-in](/pr-preview/pr-96/docs/guides/cognito-sign-in/): **Allowed callback URLs** on the app client, with Laravel and Socialite. For other providers, such as Auth0, Okta or Google, the same four steps apply. Find where the provider lists allowed callback or redirect URLs, and add the HTTPS one. ## When ngrok is still the right tool Nearhost is local-only. The name works in your browser on your laptop, and nowhere else. The sign-in round trip goes through your browser, so it does not need a tunnel. Keep one for: * **Webhooks.** A provider that sends events to your app does so from its own servers, which cannot reach your laptop. * **Sharing a link.** A colleague or a client cannot open `local.myapp.com` from their machine.

# Vite hot reload fails over SSH port forwarding

> Why Vite's scripts or hot reload fail when the dev server runs on another machine and you reach it through ssh -L, which port each setup has to forward, and how to keep it working without retyping forwards.

You run `npm run dev` on a server or a VM and forward a port to your laptop with `ssh -L`. The page loads, but edits never show up. Or the page loads without its styles and scripts. The browser console says `[vite] failed to connect to websocket`, or `[vite] server connection lost. Polling for restart...`, or the page is replaced by `Blocked request. This host ("…") is not allowed.` The first two mean the browser is asking for an address the forward does not cover. Which address depends on whether Vite serves the page itself or sits beside a backend. The third means the forward works: the request reached Vite, and Vite refused the name you used, which `server.allowedHosts` fixes. ## Why it happens Vite’s hot reload client opens a WebSocket to the host and port its own script came from, unless `server.ws` says otherwise (`server.hmr` in older Vite). So hot reload works wherever the scripts load, and fails wherever they do not. If your config sets a separate WebSocket port, such as `server.ws.clientPort`, forward that port too. ### Vite serves the page A plain Vite app, or a framework built on it, serves the page, its scripts and the hot reload socket from one port. Forward that port and the browser reaches all three: 
```sh
ssh -L 5173:localhost:5173 myserver
```
 Open `http://localhost:5173` and hot reload works. Two things still break it: * **Opening it by another name.** Vite checks the `Host` header and refuses names it does not know, the page included, with `Blocked request. This host ("…") is not allowed.` `localhost`, `*.localhost` names and IP addresses are always allowed. For any other name, add it to `server.allowedHosts` in `vite.config.js`. * **The connection dropping.** When `ssh` exits, so does the forward. The console says `server connection lost`, and nothing reloads until you run `ssh -L` again. ### Vite sits beside a backend Laravel, Rails, Django and other backends render the HTML themselves, and the page loads its scripts from the Vite dev server on a second port, at an address such as `http://localhost:5173`. In Laravel, `laravel-vite-plugin` writes that address to `public/hot` when `npm run dev` starts, and every script tag on the page uses it. Forwarding only the backend’s port loads the HTML, and then the scripts fail, because your browser asks for `localhost:5173` on your laptop and nothing listens there. Forward the Vite port too, to the same port number on your laptop: 
```sh
ssh -L 8000:localhost:8000 -L 5173:localhost:5173 myserver
```
 The number has to match on both ends. `-L 3000:localhost:5173` reaches Vite, but the page still asks for 5173. If you run several projects, each needs its own Vite port, because two forwards cannot share 5173 on your laptop. ## Keeping it working with plain SSH * **List the forwards in `~/.ssh/config`,** so one `ssh myserver` sets them all up: 
  ```plaintext
  Host myserver
    LocalForward 8000 localhost:8000
    LocalForward 5173 localhost:5173
    ServerAliveInterval 15
  ```
 * **Reconnect when it drops,** with `autossh` or a loop around `ssh -N`. With `ServerAliveInterval 15`, `ssh` notices a dead connection after about 45 seconds instead of hanging. * **Add each new name** to `server.allowedHosts` if you open the app by a name other than `localhost` or a `*.localhost` name. ## How Nearhost handles it New to Nearhost? [Install it](/pr-preview/pr-96/docs/getting-started/install/) and [add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) first. Nearhost serves the project at a name such as `https://myapp.test`, over one SSH connection per server that it reconnects by itself, putting every forward back. * **Vite serves the page.** Give its port the `web` role. The proxy passes the hot reload WebSocket through on the same origin. Add the name to `server.allowedHosts` once; with the `nearhost/vite` preset enabled, Nearhost shows the exact lines. * **Vite sits beside a backend.** Give the Vite port the `loopback` role. Nearhost forwards it to the same port number on your laptop, so the page’s `http://localhost:5173` reaches the remote dev server. Under Laravel Sail, discovery proposes this route for you. The page at `https://myapp.test` now loads its scripts from another origin, and Vite’s default CORS policy allows only `localhost` pages. `laravel-vite-plugin` also allows `*.test` names and your `APP_URL`; with another integration, add the name to `server.cors.origin`. * **Several projects.** Nearhost warns about two projects that want the same loopback port before they clash, and suggests a free one when the port comes from a variable. A loopback forward answers on both `127.0.0.1` and `[::1]`, so it also works when Vite listens on `::1` and `public/hot` says `http://[::1]:5173`. This needs Nearhost 0.7.0 or later and a laptop with the IPv6 loopback, which every Mac and almost every Linux machine has. Otherwise, see [Vite on `[::1]`](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/#vite-on-1). For the details, see [Dev servers and hot reload](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/) and [Routes and roles](/pr-preview/pr-96/docs/concepts/routes-and-roles/).

# WorkOS sign-in on a remote dev server

> Give a WorkOS AuthKit app an HTTPS redirect URI in local dev, such as https://local.myapp.com/authenticate, when the dev server runs on another machine.

New to Nearhost? [Install it](/pr-preview/pr-96/docs/getting-started/install/) and [add a server](/pr-preview/pr-96/docs/getting-started/add-a-server/) first. This guide gets WorkOS AuthKit sign-in working at `https://local.myapp.com` while your Laravel app runs on another machine. The worked example uses the `laravel/workos` package from the Laravel starter kits, but the WorkOS and Nearhost steps are the same for any stack. ## The symptom WorkOS sends the browser back to your app at a redirect URI you register in its dashboard. It has to match the URI your app sends exactly, including `https://` and the path. The staging environment accepts `http://localhost`, which is fine when the app runs on your laptop. When it runs on a server or a VM, `localhost` in your browser is not where the app is. A tunnel such as ngrok gets the page on screen, but often not much more. The app still builds its links and assets from its own idea of where it lives, so redirects and scripts point back at `localhost` or at `http://`. Each tunnel name is one more redirect URI to register, and WorkOS’s advice is to use a stable custom domain if you must use a tunnel at all. Nearhost serves the remote app on your laptop at a name you choose, with a trusted certificate, over SSH. The browser sees one stable HTTPS origin, and that is the origin you register with WorkOS. ## Pick a name Use a name under a domain you own, such as `local.myapp.com`. It needs no DNS record: Nearhost points it at your laptop through `/etc/hosts` while the project is enabled. When the project is disabled, the name resolves as it normally would. A real-domain name keeps the redirect URI shaped like the one in production. WorkOS’s documentation does not say whether it accepts `.test` names, so this guide uses a domain you own. ## Add the project On the command line, give the name with `--alias`: 
```sh
nearhost add --server mini '~/code/myapp' --alias local.myapp.com
```
 
```text
Added myapp on mini at https://local.myapp.com
Start it with `nearhost up`.
```
 A name that does not end in `.test` needs your approval, because it can hide the real site. Typing it with `--alias` counts as approval. To keep the name with the project, put it in a [`.nearhostrc`](/pr-preview/pr-96/docs/reference/nearhostrc/) in the project’s root: 
```yaml
version: 1
alias: local.myapp.com
```
 Run `nearhost add` without `--alias`, and it asks before using the name, since you did not type it: 
```text
$ nearhost add --server mini '~/code/myapp'
This project asks for these, which need your approval:
  local.myapp.com on port 8080 (a real domain)
Approve these? [y/N]
```
 See [Add a project](/pr-preview/pr-96/docs/getting-started/add-a-project/) for the rest of the add flow, and [Main name](/pr-preview/pr-96/docs/reference/config/#main-name) for how the name is approved and written to the hosts file. ## Set up WorkOS Do this in the WorkOS staging environment, which is meant for development. Its API keys, users and settings are separate from production’s. 1. In the dashboard, open **Applications**, then your application, then the **Redirects** tab. 2. Add the redirect URI `https://local.myapp.com/authenticate`, and make it the default. With `laravel/workos` the callback route is `/authenticate`. No trailing slash. 3. Set the sign-in endpoint, which WorkOS’s docs also call the initiate login URI, to `https://local.myapp.com/login`. AuthKit sends people there when sign-in starts outside your app, such as from a password reset or an invitation link. 4. On the same tab, add the sign-out URI `https://local.myapp.com/` and make it the default. Without a sign-out URI, WorkOS shows an error after sign-out, unless the app still has the older App homepage URL set. That setting is deprecated, and only kept as a fallback for existing apps. Then copy the staging environment’s client ID and API key into the app’s `.env`, after `APP_URL`, which the redirect URL builds on: 
```ini
APP_URL=https://local.myapp.com
WORKOS_CLIENT_ID=your-client-id
WORKOS_API_KEY=your-api-key
WORKOS_REDIRECT_URL="${APP_URL}/authenticate"
```
 These are the names the starter kits read in `config/services.php`. ## Set up the app `APP_URL` is set to the new name above, so the redirect URL follows it. If `APP_URL` is already further down the file, move it above `WORKOS_REDIRECT_URL`, which reads it. If you have cached the config, run `php artisan config:clear`. Nearhost’s proxy ends HTTPS on your laptop and passes plain HTTP to the server, with `X-Forwarded-Proto: https`. Laravel ignores that header until it trusts the proxy, so it thinks the request was `http://`. The WorkOS callback is unaffected, because `laravel/workos` reads it from `WORKOS_REDIRECT_URL`. What goes wrong is everything Laravel builds from the request: `route()` and `url()` links, the redirect to the dashboard after sign-in, and `asset()` URLs. The starter kit’s `bootstrap/app.php` already has a `withMiddleware` closure. Add one line inside it (Laravel 11 and later): 
```php
->withMiddleware(function (Middleware $middleware): void {
    $middleware->trustProxies(at: '*');


    // The lines already there stay as they are.
})
```
 `'*'` trusts the forwarded headers from any address. If this file also runs in production behind a known load balancer, list that load balancer’s addresses plus `127.0.0.1`, or the Docker network’s gateway under Sail, instead, or read the list from an environment variable. Nearhost’s forward arrives from `127.0.0.1`, or from the Docker network’s gateway under Sail, so leaving it out stops Laravel trusting it and brings back `http://` links. If the page loads its scripts from Vite at `http://localhost:5173`, that port needs a `loopback` route so your browser can reach it. See [Dev servers and hot reload](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/). If `public/hot` says `http://[::1]:5173` instead, the forward answers there too from Nearhost 0.7.0. With an older Nearhost, see [Vite on `[::1]`](/pr-preview/pr-96/docs/concepts/dev-servers-and-hot-reload/#vite-on-1). On another stack the idea is the same. Set the app’s public URL to `https://local.myapp.com`, and tell the framework to trust `X-Forwarded-Proto` from the proxy, so it builds `https://` links and the callback URL it sends to WorkOS matches the one you registered. ## Check it works Start the project with `nearhost up`, or from the interface, and open `https://local.myapp.com/login`. You should land on the AuthKit sign-in page, and after signing in come back to `https://local.myapp.com/authenticate` and on to the dashboard. When it does not: * **WorkOS shows an error instead of the sign-in page.** Usually the redirect URI your app sent is not on the Redirects tab of the environment whose keys you use. Compare them character by character: `https`, the host, `/authenticate`, no trailing slash. Check that `WORKOS_REDIRECT_URL` and `APP_URL` are what you expect, and that the keys are the staging ones. * **Links, the redirect after sign-in, or asset URLs use `http://`.** Laravel does not trust the proxy yet. Add `trustProxies` as above. Nearhost redirects `http://` to HTTPS, so a link may still seem to work, but `http://` scripts and styles on an HTTPS page are blocked as mixed content. Look for those warnings in the console. * **`/authenticate` returns 403.** `laravel/workos` keeps a state value in the session when you start sign-in, and refuses the callback when the session does not come back with it. Start sign-in at `https://local.myapp.com`, not at another address for the same app, and leave `SESSION_DOMAIN` unset (`null`) or set it to `local.myapp.com`. A cookie set for another domain never reaches this one. ## When you still need ngrok Nearhost is local-only. The name works in your browser on your laptop, and nowhere else. Use a public tunnel when: * **WorkOS sends webhooks.** They come from WorkOS’s servers, which cannot reach your laptop. Point the staging webhook endpoint at a tunnel. Or use WorkOS’s events API, where your app fetches events from WorkOS rather than receiving them. * **Someone outside needs the link.** A colleague or a client cannot open `local.myapp.com` from their machine. You can run both: Nearhost for your own browser, and a tunnel just for the webhook endpoint.
